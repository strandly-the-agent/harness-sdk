Probes: `/mnt/workspace/reviews/phase11-review-correctness-probe` (a scratch crate depending on the review worktree by path, default features off; run each with `cargo test --offline --test <name>` under the brief's toolchain environment).

1. `strands-rs/strands/src/agent/run.rs:305-306` (with `:212-226` and `agent.rs:728`): a call dropped while the invocation's own `AfterInvocationEvent` hooks are awaiting loses them for good. `in_pass` is cleared at `:305` before `after_invocation(..).await` at `:306`, and `abandon` records an `AbandonedRun` only `if in_pass` (`:224`), so nothing is left for the next `invoke`/`stream`/`shutdown()`, and `Drop for Agent` logs no warning. P-98(2) promises exactly this retry for the deferred replay ("a run stays pending until its hooks return", `run.rs:167-169`) but the first run of the same hooks is not covered. The hooks cut short are the SDK's own: the session manager's `AfterInvocationEvent` save (`session/session_manager.rs:489`), the memory extraction trigger, the router's state clear (`models/routing/router.rs:279`) and the background-task wait. A consumer reaches this with `tokio::time::timeout(d, agent.invoke(..))` or a `select!` while a session save is in flight; TS cannot stop there (a broken `for await` drains the generator's `finally`, `agent/agent.ts:1319-1343`). Evidence: `/mnt/workspace/reviews/phase11-review-correctness-probe/tests/after_invocation_drop.rs` (model answers, an async `AfterInvocationEvent` hook sleeps 10 s on its first call, `timeout(1 s, agent.invoke("one"))` expires, then `agent.shutdown().await`): `cargo test --offline --test after_invocation_drop` fails with `shutdown() must finish the AfterInvocationEvent hooks the drop cut short`, `left: 0, right: 1`. Fix: keep the run pending across the hooks, as `abandoned_hooks` does: before `:306` set `self.abandoned = Some(AbandonedRun { state: state.clone(), repair: None })` (or keep a second flag that `abandon` reads) and clear it when `after_invocation` returns; add the test to `agent/run/tests/drop_guard.rs`.

2. `strands-rs/strands/src/vended_plugins/skills/agent_skills.rs:89,327` (read at `:304,310,388,429,475`): per-agent skills of a shared `AgentSkills` are kept in a `HashMap<String, Skills>` keyed by `agent.id()`, and the default id of every agent is `agent`. Two agents built without an explicit id that share one plugin therefore overwrite each other's entry: the second agent's `load_skill_paths` (resolved through *its* sandbox) replaces what the first agent's prompt injection and `skills` tool read, and the map is never pruned (only `get`/`contains_key`/`insert`), so it also grows by one entry per distinct id for the life of the plugin. TS keeps a `WeakMap<LocalAgent, Map<string, Skill>>` (`vended-plugins/skills/agent-skills.ts:116,271,325`). DIVERGENCES row 137 / P-383 accept this because there is "no shared agent object across the agent views", but that premise is wrong at this commit: `AgentSandbox::owner()` (`sandbox.rs:94,136`) is the per-agent identity token that `LocalAgent` and `ToolAgent` both expose (`types/agent.rs:335,641`), and `bash` (`vended_tools/bash.rs:146-200`), `mcp_router` (`vended_tools/mcp_router.rs:231,366`) and `ModelRouter` (`models/routing/router.rs:246-252`) already key their TS-`WeakMap` state on it with `Weak<()>` and prune dead agents. Evidence: `/mnt/workspace/reviews/phase11-review-correctness-probe/tests/skills_same_id.rs` (agents A and B with default ids share one plugin over a skills directory; A is invoked, a second skill is added, B is invoked, A is invoked again): `cargo test --offline --test skills_same_id` fails with `agent A picked up the skills agent B loaded`, A's system prompt now listing `<name>two</name>`; in TS A keeps its own map until `setAvailableSkills`. Fix: key `agent_skills` as `Vec<(Weak<()>, Skills)>` on `agent.agent_sandbox().owner()` with the same `retain(strong_count > 0)` pruning as `Sessions::lock`; keep `get_available_skills(agent_id)` as a lookup by id over the live entries (or take `&Agent`), and drop DIVERGENCES row 137.

3. `strands-rs/strands/src/session/session_manager.rs:248-256,360-368` (with `:104-112`): `SessionManager::restore_snapshot(&mut agent, ..)` reaches the agent through `SnapshotTarget::local_agent_mut()` and calls `LocalAgent::load_snapshot`, so it skips the two steps `Agent::load_snapshot` wraps around it (`agent/snapshot.rs:329-341`): the background-task guard `assert_can_load_snapshot()` and the `load_app_state()` reload of the task table when the snapshot carries `state`. TS calls the agent's own method, `(params.target as LocalAgent).loadSnapshot(snapshot)` (`session/session-manager.ts:272`), which for an `Agent` is `agent/agent.ts:1628-1632` (guard, load, `_loadAppState`). The result is that a session restore on an initialized agent replaces `app_state` (including the persisted background-task records) under tasks that are still tracked, and leaves the scheduler's in-memory task table out of step with the restored state. Evidence: `/mnt/workspace/reviews/phase11-review-correctness-probe/tests/session_restore_background.rs` (the crate's own `cannot_load_a_snapshot_while_background_tasks_are_still_tracked` setup plus a session manager): `agent.load_snapshot(&snapshot)` fails with `Cannot load a snapshot while background tasks are still tracked`, and `session.restore_snapshot(&mut agent, None).await` on the same agent returns `Ok(true)`; `cargo test --offline --test session_restore_background` fails with `left: Ok(true)`, `right: Err("Cannot load a snapshot while background tasks are still tracked")`. Fix: give the sealed `SnapshotTarget` a `load_snapshot(&mut self, &Snapshot) -> Result<()>` that `Agent` implements with `Agent::load_snapshot` and `LocalAgent` with its own, and call that from `Inner::restore_snapshot` (the init-time restore keeps using the `LocalAgent` path, where the agent is not yet initialized); add the test above.

4. `strands-rs/strands/src/agent/tool_caller.rs:109-170,232-257`: a direct tool call (`agent.tool(name).invoke(..)`) does not run the hooks a dropped stream deferred (`finish_abandoned_run`, `agent/run.rs:170`), although it appends to history and fires `MessageAddedEvent` itself. P-91 says the deferred `MessageAddedEvent` for the cancel message and `AfterInvocationEvent` run on "the next `invoke`/`stream` ... or `shutdown()`"; the direct-call path was missed, so `MessageAddedEvent` subscribers see history out of order: the three direct-call messages first, and the earlier cancel message only on a later `invoke`. The subscribers are the SDK's own: the memory extraction buffer (sequence numbers follow hook order), the context manager's stash `store` hook (`experimental/context_manager.rs:584-591`) and the session manager's per-message save. Evidence: `/mnt/workspace/reviews/phase11-review-correctness-probe/tests/direct_tool_after_drop.rs` (a tool-use turn whose tool never finishes, `timeout(1 s, agent.invoke("one"))`, then `agent.tool("echo").invoke(json!({}))`): history is `[one, "Cancelled by user", toolUse, toolResult, "agent.tool.echo was called."]` while the hooks saw `["text:one", "tool_use", "tool_result", "text:agent.tool.echo was called."]`; `cargo test --offline --test direct_tool_after_drop` fails with `left: 4, right: 5`. The same gap exists for `Agent::load_snapshot` (`agent/snapshot.rs:329-341`): it replaces the history but leaves `abandoned` set (the field is only touched in `agent/run.rs` and `agent/agent.rs:455,728`), so the next call fires `MessageAddedEvent` for a cancel message that is no longer in history. The SDK does this itself: an `AgentAsTool` without `preserve_context` reloads its initial snapshot before every fresh call (`agent/agent_as_tool.rs:206-207`), so a child abandoned by a dropped parent stream replays its stale cancel message on the next delegation. Evidence: `/mnt/workspace/reviews/phase11-review-correctness-probe/tests/agent_as_tool_reset.rs` (parent dropped by a 1 s timeout while the child waits on a tool, then a second parent invocation): the child's hook log is `a` (in history), `Cancelled by user` (not in history), `b`, `child done`; `cargo test --offline --test agent_as_tool_reset` fails with `a MessageAddedEvent fired for a message that is not in history`. Fix: call `self.agent.finish_abandoned_run().await` at the top of the `ToolCallStream` body (yielding its error), and clear `abandoned.repair` (or the whole `AbandonedRun`) in `Agent::load_snapshot` when the snapshot carries `messages`; add both tests to `agent/run/tests/drop_guard.rs`.

5. `strands-rs/strands/src/vended_tools/bash.rs:155-160` (with `:167`): `bash` `restart` cannot stop a running command. `Mode::Execute` holds the session's `tokio::sync::Mutex` for the whole command (`session.lock().await.run(..)`), and `Mode::Restart` does `old.lock().await.stop()`, so a restart issued while a command runs (same batch under the default concurrent executor, or a command running as a background task) waits for that command to finish or hit its timeout (120 s by default), after which the command reports success and only then is the session replaced. TS `restart` calls `existingSession.stop()`, which kills the process at once with no lock (`vended-tools/bash/bash.ts:64-71,272-277`), and the running command fails with the session error; restart is the model's only way out of a hung command. Evidence: `/mnt/workspace/reviews/phase11-review-correctness-probe/tests/bash_restart.rs` (one model turn with `bash {mode: execute, command: "sleep 4"}` and `bash {mode: restart}`): the invocation takes `4.005 s`, the execute result is `Success`, then `Bash session restarted`; `cargo test --offline --test bash_restart` fails with `restart waited for the running command: 4.005054331s`. Fix: give each session a kill signal outside the mutex (for example a `tokio_util::sync::CancellationToken` stored next to the `SharedSession` in `Sessions.entries`); `restart` fires it without locking, and `BashSession::run` adds it as a `select!` arm that drops the process and returns `BashSessionError("Bash process exited unexpectedly ...")`.
