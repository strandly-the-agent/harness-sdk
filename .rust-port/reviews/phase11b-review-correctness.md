1. `strands-rs/strands/src/mcp/client.rs:1041-1061` (`call_once`): a `tools/call` whose future is dropped (not signalled) is never cancelled on the server, and its progress route is never removed. `notifications/cancelled` is sent only from the `signal.cancelled()` arm (`:1053-1056`), and `routes.remove(&token)` runs only there and after the response (`:1054,1061`). A dropped invocation never reaches that arm: the executor's `JoinSet` aborts the tool task before `RunGuard` cancels the signal (P-91: "tool tasks are aborted by the executor stream's `JoinSet`"), so the task is dropped, not polled again; `rmcp`'s `RequestHandle` has no `Drop` (`rmcp-3.10.0/src/service.rs:561-568`; only the explicit `RequestHandle::cancel` at `:685` notifies). The server therefore keeps running the tool to completion after `tokio::time::timeout(d, agent.invoke(..))`, a `select!` or a dropped `AgentStream`, although P-91/section 10 say every drop is a cancel, and the callback `Arc` stays in `Inner.progress.routes` for the life of the client (one entry per dropped call, since each request gets a fresh token). The same holds for any direct `McpClient::call_tool_with` future dropped by its caller. Evidence: probe `tests/mcp_drop.rs` (an `rmcp` server whose tool waits on `context.ct.cancelled()`): `signalled_cancel_reaches_the_server ... ok`, `dropped_invocation_cancels_the_mcp_request ... FAILED` with `server never saw a cancel for the dropped call: the tool keeps running` (3 s after the drop and `agent.shutdown().await`); `dropped_call_releases_its_progress_route ... FAILED`: after five `call_tool_with` futures with one progress callback were dropped, `Arc::strong_count(&callback)` is 6, not 1. Fix: hold a guard in `call_once` from the moment `send_request_with_option` returns until the response is taken; its `Drop` removes the route and, when the call did not complete, spawns `peer.notify_cancelled(CancelledNotificationParam::new(Some(id), None))` on `Handle::try_current()` (a detached send; nothing to await). Add `mcp::tests::robustness::a_dropped_call_cancels_the_request_and_frees_its_progress_route`.

2. `strands-rs/strands/src/vended_interventions/hitl.rs:386-396` (`ask_in_turn`, P-642): an answer typed for a dropped `Ask::Stdio` prompt approves the next prompt's tool. The read of a dropped prompt stays in `STDIN_READ`; when its line arrives before the next prompt takes its turn, the next prompt writes its question and `pending.get_or_insert_with(read).await` returns the already-delivered line at once, so a `y` the human typed under "Approve "read_notes"?" becomes the approval of whatever tool asks next, before the human can read that question. P-642 adopted the in-flight read so that the orphan would not swallow the next answer; it did not separate a read still waiting (the next line is the answer to the new prompt) from a read already completed (the line answered the dropped prompt). TS cannot apply an answer to a later question: each question owns its `readline` interface and later questions queue behind it (`vended-interventions/hitl/hitl.ts:26-38`). Evidence: probe `examples/hitl_stale.rs`, run as `(sleep 2; echo y; sleep 6) | hitl_stale`: invocation 1 (`read_notes`) is dropped by a 1 s timeout while its prompt waits, `y` arrives at 2.0 s, invocation 2 (`delete_everything`) starts at 3.0 s and prints `second invocation finished 0.00s after it started: ok=true delete_everything ran=true` (exit 1), with stdin still open and nothing typed after the second prompt. Fix: when a prompt takes its turn, discard an adopted read that has already resolved before showing the question (`if pending.as_mut().is_some_and(|read| !matches!(read.try_recv(), Err(TryRecvError::Empty))) { *pending = None; }`), so only a read still blocked on stdin is adopted; add `rust_only::a_line_delivered_for_a_dropped_prompt_is_not_the_next_answer` beside `a_dropped_prompt_leaves_its_read_for_the_next_prompt`, and amend P-642 and the DIVERGENCES row (`docs/DIVERGENCES.md:182`).

3. `strands-rs/strands-macros/src/expand.rs:48-136` (`tools_impl`; the generated block is `:90-106`, `tools()` `:130-134`): a `#[tool]` method under `#[cfg(..)]` breaks the build whenever the cfg is off. `#[tools]` runs before the compiler strips cfg'd items inside the impl, so it generates the `__StrandsTool` impl, the `<name>_tool` constructor and the `tools()` entry for the method unconditionally, and they call a method that no longer exists. Fix: collect the method's `#[cfg]` attributes (reject `#[cfg_attr]` that expands to `tool`, or pass it through) and put them on the generated `const _: () = { .. };` block; build `tools()` as a `let mut tools = Vec::new();` followed by one `#[cfg(..)] tools.push(ToolSource::from(self.<name>_tool()));` statement per method; add a `tests/ui/pass` case. A free `#[tool]` function is not affected: `#[cfg]` on the function itself is resolved before the attribute expands in either order (`examples/macro_cfg_fn.rs` compiles).
