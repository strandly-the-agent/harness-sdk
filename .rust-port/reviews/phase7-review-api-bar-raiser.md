3. `Cargo.toml:70-74`, `strands-rs/strands/Cargo.toml:49-51` (P-416). The move to `cedar-policy = "=4.14.0"` is the only version that resolves once the generator is a dependency: every release of `cedar-policy-mcp-schema-generator` pins one exact core (crates.io index: 0.4.0 `=4.8.1`, 0.5.0 `=4.10.0`, 0.6.0 and 0.6.1 `=4.11.0`, 0.7.0 `=4.14.0`), `cedar-policy` pins its own core exactly (`cedar-policy-4.14.1/Cargo.toml:166-167`), and `mcp-tools-sdk` must be direct because the generator doesn't re-export `ServerDescription`. 4.14.0 is also what the TS reference build runs (`node_modules/@cedar-policy/cedar-wasm/package.json` version 4.14.0), and no `cedar_policy` type is in the public API. So I agree with the pin. Three things are wrong or unrecorded:
   - The comment at `Cargo.toml:70-71` ("Any other pair compiles two copies of it") and P-416's `deny.toml` argument are incorrect: Cargo can't select two 4.x versions of one crate. Evidence: `pin2/` (`cedar-policy = "=4.14.1"` plus `cedar-policy-mcp-schema-generator = "=0.7.0"`) fails `cargo generate-lockfile --offline` with "failed to select a version for `cedar-policy-core` ... previously selected package `cedar-policy-core v4.14.1`". Fix the comment to say the pair doesn't resolve.
   - The cost to users is not recorded. Section 8.1 makes `cedar-policy` non-optional, so every `strands` user now inherits an exact pin that `strands` doesn't control, set by a 0.x crate that has trailed `cedar-policy` in every release. Evidence: `pin/` (`strands = { path = .., default-features = false }` plus `cedar-policy = "4.14.1"`) fails with "failed to select a version for `cedar-policy` ... versions that meet the requirements `=4.14.0` are: 4.14.0". The same holds for every later 4.x patch, security fixes included, until the generator republishes. `cargo tree -e normal` is 70 crates under `cedar-policy` and 66 under the generator, of 287 for `strands`. TS makes both packages optional peers (`strands-ts/package.json:428-433`), which section 7.2 maps to cargo features. This is the lead's call: either gate schema generation from `tools` (the generator and `mcp-tools-sdk`) behind a feature, which amends section 8.1's five-feature list, or keep it unconditional and write the lock-in into P-416 and the `cedar` module docs.
   - Rust uses generator 0.7.0 (core 4.14.0) while the TS build resolves the WASM generator 0.6.1 (`node_modules/@cedar-policy/mcp-schema-generator-wasm/package.json`; crate 0.6.1 pins core `=4.11.0`). Add it to P-416; whether the generated schema text matches is the parity validator's to check.
