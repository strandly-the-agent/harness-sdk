# Phase 6 correctness review (commit `0e8ee29ea`)

Failing tests cited below are in `/tmp/review6_correctness/probe/tests/` (a scratch crate with a path dependency on the review worktree; copy in `/mnt/workspace/reviews/phase6-review-correctness-probe/`). Run with the brief's toolchain env: `cd /tmp/review6_correctness/probe && cargo test --offline --no-fail-fast` (needs the worktree's `Cargo.lock` copied next to `Cargo.toml`). All five fail at this commit.

1. `strands-rs/strands/src/memory/extraction/coordinator.rs:137-158` (and `flush`, `:175-193`): each store's save queue is a `futures::future::Shared` chain. If a store's `add_messages`/`add` or an extractor panics once, the `Shared` is poisoned: every later save for that store awaits the poisoned link and panics inside its detached task (silently), the mark set at `:215` is never put back, and `flush()` panics in the caller, so `Agent::shutdown()` (`agent/agent.rs:432-433`) panics. TS settles the chain on any throw (`memory/extraction/coordinator.ts:233-249`). Evidence: `tests/coordinator_panic.rs` (first `add_messages` panics, two invokes, then `shutdown`) fails with `futures-util-0.3.34/src/future/future/shared.rs:300:25: inner future panicked during poll`. Fix: run `this.extract(..)` under `AssertUnwindSafe(..).catch_unwind()` inside the chained future and treat a panic as a failed save (restore the mark, count the failure), so a link always completes.

2. `strands-rs/strands/src/memory/memory_manager.rs:546-555` with `:343-347`: with `wait_for_writes: false` the `add_memory` tool answers `{"accepted": n}` and writes in a detached `runtime.spawn` that nothing tracks. `MemoryManager::flush` waits only for the extraction coordinator, so `Agent::shutdown()` returns while accepted writes are in flight and a runtime that stops next cancels them. In TS the fire-and-forget promise (`memory/memory-manager.ts:687-691`) is kept alive by the Node event loop; a Tokio runtime drops the task. Evidence: `tests/detached_add.rs` (store whose `add` takes 300 ms; `invoke`, `shutdown`, drop the runtime) fails: `the accepted entry was never written`, `left: 0, right: 1`. Fix: track detached writes on `Inner` (a `tokio_util::task::TaskTracker` or a pending list) and await them in `flush()`.

3. `strands-rs/strands/src/vended_plugins/skills/agent_skills.rs:250-277` (`Inner::ready`): the pending `https://` sources are removed with `std::mem::take` (`:252`) before the fetch is awaited (`:263`). If that future is dropped mid-fetch (a dropped `AgentStream` while the `BeforeInvocationEvent` hook runs, or a caller timeout around `get_available_skills`), the URLs are gone: every later call returns at once and those skills never load. TS keeps one `_ready` promise that always settles (`vended-plugins/skills/agent-skills.ts:214-261`). Evidence: `tests/skills_ready_cancel.rs` (listener that never answers, first call cancelled by `tokio::time::timeout`, then a second call) fails: `second call result: Ok([])`, 1 connection instead of 2. Fix: leave the URLs in `pending_urls` until their results are stored (clone them for the fetch, then under the lock remove exactly those and insert the skills), or restore them from a drop guard.

4. `strands-rs/strands/src/vended_plugins/skills/agent_skills.rs:176-178` with `:264-272`: `set_available_skills` swaps in a new `Resolved` while `ready()` may be awaiting the old sources' fetches; when they finish, `ready()` locks whatever `Resolved` is current and inserts the old URL skills into the replacement set. TS inserts fetch results into the `resolved` map created by that `_resolveSkills` call, so a replaced set never receives them (`agent-skills.ts:219-241`, `:186-191`). Fix: give `Resolved` a generation (or capture the target map in an `Arc` before the fetch) and drop results whose generation is no longer current.

5. `strands-rs/strands/src/storage/local_file_storage.rs:149-163` (`write_host`): the temp file is removed only when the write or rename returns an error (`:159-161`). A `write` future dropped after `tokio::fs::write` finished and before the rename (a dropped `AgentStream` during a session save or stash write, a caller timeout) leaves `<key>.__strands_tmp_<uuid>` on disk for good; `list` hides such files (`:233`), so `delete_session` and `Stash::clear` never remove them. Evidence: `tests/write_cancel.rs` fails with `orphaned temp files: ["key.json.__strands_tmp_01a1e318-..."]` (5 of 5 runs). Fix: do the temp write and rename in one `spawn_blocking` closure (it runs to completion even when the caller is dropped), or hold a drop guard that removes the temp path until the rename succeeds.

6. `strands-rs/strands/src/experimental/context_manager/stash.rs:186` (`Stash::retrieve`): stash entries are parsed with `serde_json::from_slice`, whose recursion limit is 128, while the SDK accepts tool JSON nested up to `MAX_JSON_DEPTH = 500` (`types/json.rs:16`) and TS `JSON.parse` has no such limit. A tool result nested deeper than 128 is stashed but can't be read back: `retrieve_context` fails for that reference, and `Stash::take_snapshot` (`stash.rs:249-251`) fails on it, so with a non-durable stash every later `SessionManager` save fails in `include_stash_data` (`session/session_manager.rs:287`) and is only logged. Evidence: `tests/stash_depth.rs` (store `{"json":[[..200 deep..]]}`, then `retrieve`) fails with `recursion limit exceeded at line 1 column 135`. Fix: parse with `crate::types::json::from_json_str` (as `session/snapshot_storage_adapter.rs:200` does), and in `take_snapshot` skip and log an unreadable entry instead of failing the snapshot.

7. `strands-rs/strands/src/experimental/context_manager.rs:447-469`: when a strategy returns `Ok(true)` and the recount (`:449`) then fails, the error arm runs and `any_acted` stays `false` although the history was already changed. TS sets `anyActed = true` before recounting (`context-manager/context-manager.ts:229-233`). In Rust the overflow handler (`:563-580`) then logs "no strategy made progress, skipping retry" and the overflow error surfaces after the history was reduced; the emergency strategy also keeps `overflow = true` (`:444`) and cuts again. Fix: set `any_acted = true` as soon as `apply` returns `Ok(true)`, then recount, and log a recount failure separately.

8. `strands-rs/strands/src/experimental/context_manager.rs:430` and `:449`, `strands-rs/strands/src/experimental/context_manager/strategies/offload/emergency.rs:92`: the whole-history counts call `model.count_tokens` directly. TS counts through `ModelProxy` at exactly these sites (`context-manager/context-manager.ts:212`, `:232`; `context-manager/strategies/offload/base.ts:560`), so summary blocks, injected blocks and unknown-only tool results are counted in the form the request sends. P-317 justifies the direct call with "the Rust `ModelProxy` has no `count_tokens`", which no longer holds (`models/model_proxy.rs:56`). A provider's `count_tokens` therefore sees raw `Summary`/`Injected` blocks, and the utilization gates measure a different message list than the one sent. Fix: `ModelProxy::new(&*model).count_tokens(..)` at the three sites (per-block counts stay direct, as in TS `base.ts:463`, `:511`).

9. `strands-rs/strands/src/vended_plugins/skills/skill.rs:320`: `reqwest::Client::new()` panics when the TLS backend or the system resolver configuration can't be initialised (`reqwest-0.13.5/src/async_impl/client.rs:2516-2524`: `ClientBuilder::new().build().expect("Client::new()")`), so `Skill::from_url` and the `AgentSkills` URL fetch can panic in library code instead of returning the `failed to fetch skill` error. The providers already use the fallible form (`models/openai.rs:470`, `models/anthropic/client.rs:245`). Fix: `reqwest::Client::builder().build().map_err(|error| error.to_string())?`.

Verdict: not ready to close; findings 1-3, 5 and 6 lose data or panic on reachable paths and each has a failing test, the rest are small, local fixes.
