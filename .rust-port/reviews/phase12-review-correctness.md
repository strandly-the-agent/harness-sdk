## Findings

**correctness-1.** `harness-rs/strands-harness/src/agent.rs:684-700` (`session_storage`): a session directory with no final path component (`"."`, `".."`, `"/"`, `"x/.."`) is stored under an extra `session/` folder, so the snapshot layout differs from TS and from every other `dir`. The function marks the storage as namespaced only when `Path::file_name()` exists; otherwise it returns a plain `LocalFileStorage::new(dir)`, and `SessionManager` adds its own `session` namespace to an un-namespaced storage (`strands-rs/strands/src/session/session_manager.rs:206-211`). The stash still goes to `<dir>/<id>` (`agent.rs:514`), so one session's two halves land in different folders. TS always writes `<dir>/<id>/scopes/...` (`harness-ts/src/agent.ts:450-457`).
Evidence: `probe.rs::session_dir_dot_layout` (session `{ id: "checkpoint", dir: "." }`, one mock turn) lists `session/checkpoint/scopes/agent/agent/snapshots/snapshot_latest.json`; the same options in TS (`ts-diff/sess.ts`) give `checkpoint/scopes/agent/agent/snapshots/snapshot_latest.json`.
The same split also makes a directory whose last component contains a backslash (a legal name on Unix) an error, because the component is passed to `namespace()`: `probe.rs::session_dir_with_backslash` (`dir: "we\\ird"`) fails with `Invalid storage prefix 'we\ird': backslashes are not allowed`; TS (`ts-diff/bs.ts`) creates the folder.
Fix: build it as `memory.rs:101` does, `LocalFileStorage::new(dir).with_namespace("")?`, and drop the parent/file-name split. Add tests with `dir: "."` and a backslash.

**correctness-2.** `harness-rs/strands-harness/src/config/options.rs:162-210` (`apply_agent_config`): portable `agentConfig` keys that TS applies and Rust can express are dropped with a warning, and one is rejected. TS spreads `agentConfig` into the options first and only overrides the keys the config sets (`harness-ts/src/config.ts:370-393`), then spreads the rest into `new Agent` (`harness-ts/src/agent.ts:364,512`). Rust:
- drops `traceAttributes` and `toolExecutor`, although `AgentConfig::trace_attributes` and `AgentConfig::tool_executor` exist (`strands-rs/strands/src/agent/config.rs:377,384`); `sandbox: false` (`SandboxSource::Off`) and `retryStrategy: null` go the same way;
- fails on the object form of `backgroundTasks` (`options.rs:197` parses a `bool` only), although `BackgroundTasksConfig` has the same `agentic`/`always`/`never` lists;
- drops the harness-level keys TS honours there when the top-level key is at its default: `instructions`, `caching`, `builtinTools`, `builtinPlugins`, `mcpServers`, `interventions`.
`DIVERGENCES.md:41` gives the reason as "the other keys have no JSON form in Rust", which does not hold for these. PROMPT.md section 11 item 37 forbids accepted-but-ignored config.
Evidence: `probe.rs::agent_config_trace_attributes` prints `trace_attributes={} tool_executor=false` and returns `Ok`. `probe.rs::agent_config_background_tasks_object` fails with `agentConfig.backgroundTasks is invalid: invalid type: map, expected a boolean`. Differential `ts-diff/odiff.ts` against `optdiff.rs`, case 35: TS returns `{"builtinPlugins":[],"builtinTools":["read"],"caching":false,"instructions":"from-agent-config","interventions":"ask","mcpServers":{"z":{"command":"z"}},...}`, Rust returns none of them.
Fix: map the keys listed above; return an error for the keys that really have no Rust form instead of warning; correct the `DIVERGENCES.md` row.

**correctness-3.** `harness-rs/strands-harness/src/agent.rs:732-746` (`select_builtin_plugins`) and `:703-705` (`has_skills`): plugins are recognised by `name()`, so a consumer `Todos` built with a custom name makes `create_harness` fail, and a consumer `EnvironmentContext` with a custom name gets a second, built-in one. TS skips the built-in when the consumer list holds an instance of the class (`harness-ts/src/agent.ts:257`). P-958 and `DIVERGENCES.md:50` record the by-name rule and "a second default one is added", not these two consequences.
Evidence: `probe.rs::consumer_todos_with_custom_name` fails with `Tool name "todo_write" is registered more than once (from a built-in plugin and plugins). Rename the tool you passed, or drop the built-in via builtinTools / builtinPlugins.` `probe.rs::consumer_environment_with_custom_name` finds 2 `<environment>` blocks in the first request. TS with both custom-named plugins (`ts-diff/envdup.ts`) builds, lists one `todo_write` and sends 1 block.
Fix: recognise the type: an `as_any` (or `type_id`) on the SDK `Plugin` trait, as P-958 already proposes. Until then, state both consequences in `DIVERGENCES.md`.

**correctness-4.** Secrets in `Debug` output; the 12a fix for correctness-a8 is incomplete in two places.
- `harness-rs/strands-harness/src/config.rs:514-522`: `HarnessConfigMcpServers` derives `Debug`, so `{:?}` of a `HarnessAgentConfig` prints the values under each server's `env` and `headers`. Evidence: `probe.rs::portable_config_debug_prints_mcp_secrets` prints `mcp_servers: Servers({"one": Object {"command": String("run"), "env": Object {"TOKEN": String("s3cret")}, "headers": Object {"x-key": String("hunter2")}}})`.
- `harness-rs/strands-harness/src/agent.rs:60-71`: the hand-written `Debug` of `McpServersOption` redacts `env` and `headers` only. A server entry can carry OAuth client credentials (`auth: { clientId, clientSecret }`, `strands-rs/strands/src/mcp/config.rs:69`), which the SDK's typed `McpClientCredentials` redacts (`mcp/client.rs:127-135`). Evidence: `probe.rs::mcp_servers_option_debug_prints_client_secret` prints `"auth": Object {"clientId": String("id"), "clientSecret": String("s3cret")}`, and `{:?}` of the whole `HarnessAgentOptions` contains the secret.
Fix: one shared redaction function that covers `env`, `headers` and `auth.clientSecret`, used by a hand-written `Debug` on both types.

**correctness-5.** `harness-rs/strands-harness/src/agent.rs:313,579-594` (the `subagent` tool is forced into `always` background) with `strands-rs/strands/src/background_tasks/background_tasks.rs:537-541`: when a child interrupts after the parent's model has ended its turn (for example `interventions: "ask"` approving a child tool), the resumed parent invocation calls the model with a history that ends in an assistant message, and the next call carries two assistant messages in a row. The interrupt itself is delivered and resumed correctly through `AgentResult::interrupts`, in the background and with `background_tasks: false` (section 11 item 47 holds). TS does exactly the same (`strands-ts/src/background-tasks/background-tasks.ts:275-277`), so this is a shared defect, not a port error; the harness makes it the default path. Not tested against a live provider, so whether Bedrock or Anthropic reject such a request is not verified here.
Evidence: `interrupt.rs::child_interrupt_default_background` (default harness, `interventions: "ask"`; the parent delegates, says "parent waits", the child asks to approve `shell`, the caller answers `"y"`): `REQ3 roles=User["text"] | Assistant["toolUse"] | User["toolResult"] | Assistant["text"]`, `REQ5 roles=... | Assistant["text"] | Assistant["text", "toolUse"] | User["toolResult"]`. `ts-diff/intr.ts` prints the same two role sequences.
Fix: record it in `.rust-port/ts-bugs.md` and decide for both SDKs: skip the model call on a resume that added no message (wait for the task and deliver its result as the continuation), or document the limit.

**correctness-6.** `harness-rs/strands-harness/src/builtin_tools.rs:287,321` with `strands-rs/strands/src/mcp/agent_tools.rs:34-45`: after the first delegation the parent stops refreshing its MCP tools. A child is built from the parent's `McpClient` (the same connection, as section 11 item 43 requires), and the child's `initialize` calls `client.set_on_tools_changed(..)`, a single slot (`mcp/client.rs:755-757`): it replaces the parent's callback with one that holds a `Weak` to the child's queue. Once the child is dropped the callback does nothing. TS has the same single slot (`strands-ts/src/agent/agent.ts:885`), so the defect is shared; the harness's client sharing is what exposes it.
Evidence: `mcp.rs` with a stdio MCP server (`mcp/server.py`; its `mutate` tool adds a tool `extra` and sends `notifications/tools/list_changed`). `control_refresh_without_delegation`: the parent's fourth request lists `srv_extra`. `refresh_after_delegation`: the server log shows the refresh (`tools/list` right after `tools/call mutate`), yet `req3..req5 tools=["subagent", "srv_echo", "srv_mutate"]`. `ts-diff/mcp.ts` gives the same two results.
Fix: let the notification fan out (subscribers per agent, removed with the agent) in `McpClient`, or chain the previous callback in `agent_tools::initialize`; add an SDK test with two agents on one client; record the TS side in `.rust-port/ts-bugs.md`.

**correctness-7.** `harness-rs/strands-harness/src/config/normalize.rs:604-609` (`subagent_config`): `builtinTools.subagent.maxDepth` above `u32::MAX` is rejected with `must be a non-negative integer.`, which does not describe the value. TS accepts any non-negative safe integer (`harness-ts/src/config.ts:205-209`).
Evidence: differential `ts-diff/diff.ts` against `cfgdiff.rs`, case 49 (`{"builtinTools": {"subagent": {"maxDepth": 5000000000}}}`): `ok` in TS, `Invalid agent config:\nbuiltinTools.subagent.maxDepth must be a non-negative integer.` in Rust.
Fix: saturate to `u32::MAX` (the guard only compares the remaining depth with zero), or keep the rejection and list it in `DIVERGENCES.md`.

**correctness-8.** `harness-rs/strands-harness/src/telemetry.rs:93,133` and `src/lib.rs:22`: with `OTEL_TRACES_EXPORTER=otlp`, a harness process that ends soon after its last invocation exports no spans, and the caller cannot flush. `create_harness` keeps the tracer provider in a private static; `shutdown_telemetry` is `pub(crate)` and dead code, and the `telemetry` module is private. P-923 leaves this open on the ground that "harness-ts never shuts the provider down"; the TS SDK flushes on exit by itself (`strands-ts/src/telemetry/config.ts:213-214`, `process.once('beforeExit', ...forceFlush())`), so TS keeps the spans and Rust loses them.
Evidence: `src/bin/otelprobe.rs` (mock model, one `invoke`, `agent.shutdown().await`, exit) against a local listener (`otlp_server.py`) with `OTEL_TRACES_EXPORTER=otlp OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:43181 OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`: exiting at once, the listener saw 0 requests; staying alive 7 s after the invocation, it saw `POST /v1/traces 15296 bytes`.
Fix: make the flush reachable: export `shutdown_telemetry` and name it in the crate docs next to `OTEL_TRACES_EXPORTER`, or return a guard from a public setup function; add a test that a span reaches an in-memory exporter after the public call; update P-923.

**correctness-9.** `strands-rs/strands/src/agent/run.rs:807,864` (outside the phase diff; found through the run for correctness-6): tool-registry changes made in a `BeforeModelCallEvent` hook reach the model one call late. The loop reads `tool_specs` before it invokes the hooks (`run.rs:807`, hooks at `:820`) and passes that copy to the model (`:864`). TS reads the registry again when it builds the model call, after the hooks (`strands-ts/src/agent/agent.ts:2600`). The SDK's MCP refresh applies `tools/list_changed` in such a hook (`mcp/agent_tools.rs:46-57`), so a tool the server added is offered a call later than in TS, and a removed tool is offered once more.
Evidence: the `control` run of correctness-6 with 300 ms turns: TS lists `srv_extra` in `req2`, Rust in `req3`; the refresh `tools/list` is in the server log before `req2` in both.
Fix: read `tool_registry().tool_specs()` after the `BeforeModelCallEvent` hooks; add a test with a hook that registers a tool and asserts it is in that call's `tool_specs`.
