Evidence: probe `tests/drop.rs::dropped_stream_ends_spans` (drop the stream while a tool sleeps) fails: the exporter holds only `chat` (OK) and `execute_tool slow status=Unset end_time_attr=false`; no `invoke_agent dropper`. `invoke_after_drop` shows the exporter unchanged 10 minutes later, and only the next `invoke` flushes `execute_agent_loop_cycle status=Unset end_time_attr=false` and `invoke_agent dropper status=Unset end_time_attr=false` (their OpenTelemetry end timestamps are then the time of the next invocation). TS closes all of them when the consumer closes the iterator: `agent/agent.ts:2673-2679` (model span, `finally`), `agent/agent.ts:1755-1770` (`closeCycle`: `endCycle` + `endAgentLoopSpan` "however the cycle exits ... or the consumer closing the public iterator"), `agent/agent.ts:2090-2107` (`endAgentSpan` in `finally`). By reading (not probed): the same task abort (`executor.rs:91`, "Dropping it aborts the tool tasks still running") hits the sibling tools of a concurrent batch when `ToolBatch::handle` returns an error (`executor.rs:181,207,211,223`). Fix: in `abandon` (already synchronous on drop) lock telemetry and run `tracer.end_model(&ModelSpanEnd::default())`, `meter.end_cycle(..)`, `tracer.end_cycle(None)`, `tracer.end_agent(None, None, &usage, None)` as the TS `finally` blocks do; in `ToolTerminal::stream` and `ModelTerminal::stream` hold a drop guard that calls `end_tool`/`meter.end_tool_call` (resp. `end_model`) when the stream is dropped before its normal end.

2. `src/telemetry/config/setup.rs:172` (`tracing_subscriber::registry().with(tracing_layer(provider))`) and `:183-188` (`tracing_layer`): the layer has no filter, so the subscriber `setup_tracer` installs (a) exports every `tracing` span of every crate at every level as an OpenTelemetry span of the service tracer (the lockfile's `h2` 0.4.20 has 26 `trace_span!`/`debug_span!` sites, `aws-smithy-runtime` 1.16.3 12, `aws-config` 10), (b) turns every `tracing` event emitted while an `execute_tool` or memory span is current into a span event, which counts against the SDK's 128-events-per-span limit and evicts the tool's own `gen_ai.choice`, and (c) enables every TRACE callsite process-wide (a bare registry gives no max-level hint). Evidence: probe `tests/layer.rs` over exactly that subscriber: `only_agent_spans_are_exported` fails with `["chat", "FramedRead::poll_next", "execute_tool chatty", ...]`; `tool_result_event_survives_dependency_logging` (a tool whose dependency logs 200 `trace!` lines) fails with `gen_ai.choice dropped; 128 events kept, 74 dropped`; `error_log_in_tool` prints the log line as a span event (`["gen_ai.tool.message", "handled, recovered", "gen_ai.choice"]`). TS exports only the spans `Tracer` starts from `trace.getTracer(serviceName)` (`telemetry/tracer.ts`), and log lines are never span events. Fix: in `setup_tracer` wrap the layer in a per-layer filter that passes spans only (`filter_fn(|meta| meta.is_span() && meta.target().starts_with("strands"))`, or `is_span() && *meta.level() <= Level::INFO` if tool-internal spans should nest), and document the same filter next to `tracing_layer` for applications that add it to their own subscriber; probe `tests/filter.rs::filtered_layer_keeps_agent_spans_events_and_attributes` passes with the first filter: the six agent spans keep their parents, statuses, `trace_attributes` and `gen_ai.*` events (`OpenTelemetrySpanExt::{set_attribute, add_event}` don't go through the filter), and the foreign span and the 201 log events are gone.

3. `src/memory/extraction/coordinator.rs:177` (`runtime.spawn(next.clone().in_current_span())`) and `src/memory/memory_manager.rs:625` (`runtime.spawn(writes.in_current_span())`): the detached save holds a handle to the span that scheduled it, and `tracing-opentelemetry` ends (and exports) an OpenTelemetry span only when its last `tracing` handle is dropped, so that span and its ancestors (a `tracing` child keeps its parents open) stay open until the background save finishes; their end timestamps are the save's end. Evidence: probe `tests/extract.rs::the_callers_span_closes_when_the_invocation_returns` (a store whose `add_messages` takes 2 s, `InvocationTrigger`, `agent.invoke(..).instrument(request)`) fails: `invoke returned after 9.9ms`, yet `request exported 2.001804895s after invoke returned`; the worktree's own test says so (`src/memory/memory_manager/tracing_tests.rs:403`, "The spawned driver of the save holds the caller span"). By reading (not probed): for a sub-agent run as a tool the held span is the parent's `execute_tool` span (the tool future is instrumented with it, `executor.rs:597`), which keeps the parent's cycle and `invoke_agent` spans unexported too; `memory_manager.rs:625` (`add_entries`) is called only from the memory add tool's handler (`memory_manager.rs:596`), i.e. inside an `execute_tool` span. TS ends each span at its `end*Span` call regardless of detached work (`memory/extraction/coordinator.ts:237` only activates the extract span around the write). `memory.extract` is a root span with an explicit link (`coordinator.rs:249-254`, `tracer/memory.rs` `link_parent`), so the handle buys nothing there. Fix: spawn both detached drivers without the caller's span (`runtime.spawn(next.clone())`; for the detached add, if its `memory.add` spans should stay under the tool span, capture `Span::current().context()` before spawning and set it as their OpenTelemetry parent with `OpenTelemetrySpanExt::set_parent` (not probed)), and note the exception next to rule 42d.

4. `src/telemetry/config/setup.rs:168-171,232`: `setup_tracer` replaces the process-global text-map propagator (`global::set_text_map_propagator`) also when the caller passed its own `provider`, silently discarding a propagator the application registered alongside that provider (B3, X-Ray, ...). 5. `src/telemetry/config/setup.rs:159-160,240` (the docs telling the caller to "Call `shutdown()` on the returned provider before the process exits") with P-490's "nothing blocks a runtime thread": exports do run on the SDK threads, but the documented `shutdown()` is a blocking wait on them. Evidence: `/tmp/ct-review-r10/debug/setup current refused` (probe `src/bin/setup.rs`, `setup_tracer` + `setup_meter` with `otlp: true` on a `current_thread` runtime, endpoint refusing connections): `tracer.shutdown` 722 ms, `meter.shutdown` 849 ms, and a 50 ms heartbeat task stalled for 1.62 s; with an endpoint that accepts but never answers (`multi https`) each call blocks 5.0 s (`Err(InternalFailure("Shutdown errors: [Timeout(5s)]"))`). Setup itself (61 ms, inside either runtime flavor, no panic), repeat calls and the export path behaved as P-488/P-490 describe. Fix: say in both doc comments that `shutdown()` blocks until the exporter flushes or times out and must run off the runtime (`tokio::task::spawn_blocking(move || provider.shutdown())`), and do that in the Phase 12 harness exit path.

6. `src/telemetry/tracer.rs:652-656` (`record_trace_attributes`) with `:399-421`, `:659-677`: a `trace_attributes` key that equals a standard key is exported twice on the same span, once from the `tracing` field and once from `set_attribute`; OTLP attribute keys must be unique and backends pick either value. Evidence: probe `tests/filter.rs::trace_attribute_overrides_a_standard_key_once` (`trace_attributes = {gen_ai.agent.name: "override", gen_ai.usage.total_tokens: 999}`) fails: the `invoke_agent` span carries `gen_ai.agent.name -> ["a", "override"]` and `gen_ai.usage.total_tokens -> ["999", "0"]`.
