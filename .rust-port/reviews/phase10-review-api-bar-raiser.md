Evidence is in `/tmp/review10_api-bar-raiser/` (sources, scripts and `RESULTS.md` are also copied to `/mnt/workspace/reviews/phase10-review-api-bar-raiser-probe/`): `scratch/` depends on the review worktree by path (`./run.sh <file> [--features otel]` runs `cargo check` with that file as `src/lib.rs`), and `usage/` is an application-style crate with its own `opentelemetry_sdk`, `opentelemetry`, `tracing-subscriber` and `tokio` dependencies (`./runu.sh <file> [test]`). `cargo check -p strands --no-default-features` and `--no-default-features --features otel` both pass, and `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps` passes for both feature sets.

Environment note: the root filesystem reached 100% during the review (`/tmp/ct-review-r10` 9.8 GB, `/tmp/ct-p7fixa` 9.8 GB, `/tmp/ct-p7fixb` 8.6 GB). I removed only my four scratch crates' own outputs from the shared target dir and ran no builds after that; every result below was observed before.

1. `src/telemetry/mod.rs:13-22`: two of the four functions TS exports from the telemetry entry point are missing. `telemetry/index.ts:36` exports `setupTracer, getTracer, setupMeter, getMeter` (`telemetry/config.ts:101-103,125-127`, each with an `@example`); Rust has no `get_tracer` or `get_meter`, and no entry in `DECISIONS-pending.md`, `DIVERGENCES.md` or `ts-bugs.md` says why (`grep -c -i 'get_tracer\|getTracer\|get_meter'` is 0 in all three apart from the unrelated mention in P-486). `docs/PARITY.md:290` and `docs/reviews/live.md:54` say "their Rust API is being built by another track". Evidence: `missing_exports.rs` fails with `E0425: cannot find function 'get_tracer'` and `'get_meter' in module 'strands::telemetry'`. `get_tracer_feasible.rs` passes: a span from `opentelemetry::global::tracer(..)` started inside a `tracing` span parents under it once `setup_tracer` has run, so the TS use (custom spans under the agent's) works. Fix: under `otel`, add `pub fn get_tracer() -> opentelemetry::global::BoxedTracer` (`global::tracer(service_name(&process_env))`) and `pub fn get_meter() -> opentelemetry::metrics::Meter` (the `global::meter_with_scope` call of `src/telemetry/meter.rs:351`) and re-export them; or log the omission as a decision with a `DIVERGENCES.md` row that tells users to open `tracing` spans instead.

2. `src/telemetry/config/setup.rs:172,187`: the subscriber `setup_tracer` installs exports more than the agent's spans, and nothing an application passes to `setup_tracer` can change that. It is `registry().with(tracing_layer(provider))` with no filter and the layer's defaults. Evidence: `layer_output.rs` builds exactly that subscriber over a recording exporter and runs a mock agent. Every agent span carries eight attributes TS never sets (`code.file.path`, `code.module.name`, `code.line.number`, `thread.id`, `thread.name`, `target`, `busy_ns`, `idle_ns`), and a `trace_span!` with a `trace!` event standing in for a dependency is exported as a span with the log line as a span event. The repo's own live test filters "the spans of the HTTP and AWS clients" out of its recording for the same reason (`tests/live_telemetry.rs:59-75`). In TS only spans started through the OpenTelemetry tracer export, and `logger` calls never become span events. `docs/DIVERGENCES.md:173` explains the extra attributes with "the layer belongs to the application", which is not true on the `setup_tracer` path: the SDK builds the layer. Fix (`layer_output_fixed.rs` shows it removes all eight attributes and the dependency span, and keeps every agent span and event): in `tracing_layer`, `.with_location(false).with_threads(false).with_tracked_inactivity(false).with_target(false)`; in `setup_tracer`, add `.with_filter(LevelFilter::INFO)` to the layer (the agent spans are `info_span!`); correct the `DIVERGENCES.md` row. Not run: a span-only filter (`filter_fn(|metadata| metadata.is_span() && ..)`) would also stop `tracing` log lines at info and above from becoming span events; the SDK's own span events go through `OpenTelemetrySpanExt::add_event` and wouldn't be affected.

3. `src/telemetry/config/setup.rs:165-179,201-210,232`: `setup_tracer` with a custom provider replaces the application's global propagator. TS returns right after `trace.setGlobalTracerProvider(_customProvider)` (`telemetry/config.ts:191-199`) and documents "when a custom provider is passed, the caller is responsible for their own context manager / propagator setup" (`config.ts:170-171`); Rust runs the same `register` closure for both branches, so `global::set_text_map_propagator` always runs. P-488 does not log this. Evidence: `custom_provider_propagator.rs` (`./runu.sh custom_provider_propagator.rs test`) sets a baggage-only global propagator, calls `setup_tracer(TracerConfig::builder().provider(provider).build())` and fails with `left: ["traceparent", "tracestate", "baggage"] right: ["baggage"]`. Fix: set the propagator only in the `None` branch (pass the branch to `register`, or set it where the provider is built), and say so in the rustdoc at `setup.rs:154-160`.

4. `src/telemetry/mod.rs:14-20`: the crates whose types make up the `otel` API are not re-exported. `TracerConfig::provider` and the return type of `setup_tracer` are `opentelemetry_sdk::trace::SdkTracerProvider`, `MeterConfig::provider` is `SdkMeterProvider`, `BaggageSpanProcessor` exists to be passed to `opentelemetry_sdk`'s `with_span_processor`, `tracing_layer` returns `tracing_opentelemetry::OpenTelemetryLayer<S, SdkTracer>` bounded on `tracing_subscriber::registry::LookupSpan`. Evidence: `missing_exports.rs` fails with `E0433: cannot find 'opentelemetry_sdk' / 'opentelemetry' / 'tracing_opentelemetry' / 'tracing_subscriber' in 'telemetry'`. Fix: under `otel`, `pub use {opentelemetry, opentelemetry_sdk, tracing_opentelemetry, tracing_subscriber};` in `src/telemetry/mod.rs`.

5. `src/agent/config.rs:304-309`: the two new `AgentConfig` setters take an `indexmap::IndexMap` and `strands` does not re-export `indexmap`. TS writes `traceAttributes: { 'session.id': 'abc' }` (`agent/agent.ts:281,286`). Evidence: `trace_attrs.rs`: `strands::indexmap` and `strands::telemetry::indexmap` are E0433, and `.trace_attributes([("session.id".to_owned(), AttributeValue::from("abc"))])` and `.baggage_attributes([("tenant".to_owned(), "a".to_owned())])` are E0308; only `[..].into_iter().collect()` compiles without an `indexmap` dependency.
