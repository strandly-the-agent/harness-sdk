# Phase 7 correctness review (commit 0e8ee29ea)

Probes use the public API only and build against the review worktree: `/tmp/review7_correctness/probe` (`tests/hitl_stdio.rs`, `tests/cedar_panics.rs`, `tests/interrupt_order.rs`, `tests/cedar.rs`). The `hitl_stdio` binary is run directly with stdin piped (`/tmp/review7_correctness/hitl_stdio_bin`, built by `cargo test --offline --test hitl_stdio --no-run`).

1. `strands-rs/strands/src/vended_interventions/hitl.rs:336-357` (`stdio_ask`): a dropped approval prompt leaves its `spawn_blocking` stdin read running. The `_turn` guard (line 342) dies with the dropped future, so the next prompt starts a second read behind the orphan; the orphan consumes the human's next line and discards it, and dropping the `Runtime` blocks until a line arrives. TS never abandons the read (`vended-interventions/hitl/hitl.ts:26-39`; TS cancellation is cooperative, a Rust caller can drop the invocation). Evidence: `(sleep 3; echo n; sleep 3; echo y; sleep 2) | hitl_stdio_bin --exact dropped_prompt_swallows_the_next_answer_shared_handler --nocapture`: the first invocation is dropped by a 500 ms `tokio::time::timeout`, the second prompt (the only live one, same `HumanInTheLoop`) is answered `n`, and the result is `elapsed=5.39s tool_calls=1` (the `n` went to the orphan, the later `y` approved the call); same result with two handlers (`dropped_prompt_swallows_the_next_answer`). `(sleep 4; echo y) | hitl_stdio_bin --exact runtime_shutdown_waits_for_the_dropped_prompt --nocapture`: `runtime drop took 3.35s`. Fix: read on a detached `std::thread` that answers over a `oneshot` (not the runtime's blocking pool), and keep the in-flight receiver in the queue mutex so the next prompt adopts a pending read instead of racing it: `let mut slot = queue.lock().await; let rx = slot.get_or_insert_with(spawn_reader); let answer = (&mut *rx).await; *slot = None;` with `queue: tokio::sync::Mutex<Option<oneshot::Receiver<io::Result<String>>>>` in a process-wide `static` (stdin is per process).

2. `strands-rs/strands/src/vended_interventions/hitl.rs:344-349`: the `StdoutLock` taken at line 344 is still held while line 348 blocks in `read_line`, so every other stdout writer in the process (another agent's printer, a tool in the concurrent executor, a `tracing` fmt layer on stdout) blocks until the human answers; with finding 1 an orphaned prompt holds it until the next line. TS writes the prompt through `readline` and holds nothing (`hitl.ts:28-35`). Evidence: `(sleep 4; echo y) | hitl_stdio_bin --exact pending_prompt_blocks_other_stdout_writers --nocapture`: `stdout write on another thread took 3.26s`. Fix: scope the lock to the prompt (`{ let mut stdout = std::io::stdout().lock(); write!(stdout, ..)?; stdout.flush()?; }`) before reading. That lock is today the only thing serialising the prompts of two `HumanInTheLoop` instances (the `queue` at line 338 is per instance), so make the queue process-wide in the same change (the slot of finding 1).

3. `strands-rs/strands/src/models/routing/router.rs:510`: `state.switches += 1` is an unchecked add on a `u32` counter. `.rust-port/PROMPT.md` section 11 rule 15 ("`Usage::accumulate` and every counter use saturating arithmetic") and `strands-rs/AGENTS.md:69` require saturating ops; the neighbouring counter does it (`agent/run.rs:1002`, `attempt_count.saturating_add(1)`). A wrap in a release build would reopen the `max_switches` cap checked at `router.rs:442`; a debug build panics. Fix: `state.switches = state.switches.saturating_add(1);`.

4. `strands-rs/strands/src/vended_interventions/cedar.rs:52-60` with `cedar/schema_generator.rs:36-40`: `ToolDefinition::new(name)` ("A tool with no input schema or description") builds a definition that schema generation always rejects, and the error names neither the tool nor the missing field. Evidence: `cargo test --offline --test cedar_panics -- --nocapture` in the probe crate: `CedarAuthorizationConfig { policies: "permit(principal, action, resource);", tools: Some(vec![ToolDefinition::new("search")]), .. }` gives `Err("Schema generation failed: Missing expected attribute")`; the same tool with `input_schema: {"type":"object",..}` succeeds. The TS WASM generator also rejects a tool without `inputSchema` (`node /tmp/review7_correctness/gen.mjs`: `Invalid tool descriptions: failed to parse JSON`), so the constructor has no working use. Fix: check in `generate_schema` before serialising and return `Schema generation failed: tool=<name> has no inputSchema`, and make the constructor take the schema (`ToolDefinition::new(name, input_schema)`).
