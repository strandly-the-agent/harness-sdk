# Phase 12a correctness review (commit 087a6f158)

Reviewed 19:30-19:58 UTC. Scratch tests: `/tmp/reviewh12_correctness/probe/tests/{ptc,cancel}.rs` (path dependency on the review worktree, own target dir, public API only). Run one with `cargo test --offline --test ptc <name> -- --nocapture` from `/tmp/reviewh12_correctness/probe`.

1. `harness-rs/strands-harness/src/tools/programmatic_tool_caller/run.rs:62-70`: a cancelled step keeps a tokio blocking-pool thread spinning until the VM's 60 s limit, and tokio's runtime shutdown waits for blocking tasks, so after a cancel on a busy guest loop the host cannot exit for up to a minute. `DIVERGENCES.md:27` records the abandoned step but not this consequence. Evidence: `cancel.rs::a_cancelled_busy_loop_does_not_hold_the_runtime_open` (a `MockMessageModel` turn calls `programmatic_tool_caller` with `while True: pass`; `cancel_handle().cancel()` after 300 ms) prints `invoke returned after 317ms: Ok(Cancelled)` and then `runtime drop took 59.695s`. The crate's own `a_cancel_does_not_wait_for_a_busy_loop` measures only the first half. Fix: run interpreter steps on a dedicated detached `std::thread` with the result over a `oneshot`, not `spawn_blocking`; the thread still burns CPU until the limit, but nothing waits for it.

2. `strands-rs/strands/src/tools/executors/executor.rs:296-305` (`call_tool`): a failing `ExecuteToolStage` middleware loses its error. `ToolTask::execute` sends `TaskMessage::Failed` and returns `None` in the same poll (`executor.rs:415-418`), so the `select!` resolves on the `execute` branch with `(None, None)` and the queued `Failed` is never read; the `Failed` arm at `:332` is unreachable in practice. Evidence: `ptc.rs::middleware_failure_text_reaches_call_tool` (an `ExecuteToolStage::input` returning `MiddlewareError::Failed(Error::other("input middleware failed"))` for `echo`) fails; the guest sees `RuntimeError: Failed to execute tool 'echo': the tool call ended without a result`. Fix: when `execute` yields `None`, drain `receiver.try_recv()` first (`Failed` -> `Err(error)`, `Interrupted` -> push) before choosing the outcome; add the case to `types/agent/tests.rs`.

3. `harness-rs/strands-harness/src/tools/programmatic_tool_caller.rs:46,159-162,275-283`: `INSTANCES` is process-global mutable state keyed by name that never shrinks (section 7.5; TS keeps a `WeakSet<Tool>` of identities, `programmatic-tool-caller.ts:56,373,574`). A caller name made anywhere in the process, even for a tool already dropped, hides every same-named ordinary tool from every caller of every agent. Evidence: `ptc.rs::a_tool_sharing_a_name_with_an_unrelated_caller_is_still_exposed` fails with `NameError: name 'lookup' is not defined` after an unrelated, dropped `make_programmatic_tool_caller(name: "lookup")`. I disagree with P-873, which accepts this. Fix: mark the tool itself (a private marker the registry tool can be asked for, such as an `as_any`-style hook on the SDK `Tool` or a tag on `FunctionTool`) and filter on that; failing that, keep `(name, Weak<()>)` pairs whose `Arc<()>` lives in the handler, so a dropped caller stops reserving its name.

4. `harness-rs/strands-harness/src/tools/programmatic_tool_caller/run.rs:62-66`: in a dev-profile build, guest code aborts the host process. Monty bounds data recursion by depth (about 1000), not by stack, and debug frames do not fit that depth in the blocking pool's 2 MiB stack. Evidence (dev profile): `a = []` / `for i in range(500): a = [a]` / `print(await echo(x=a))`, and the same list at depth 3000 through `str(a)` or `json.dumps(a)`, end with `thread 'tokio-rt-worker' has overflowed its stack / fatal runtime error: stack overflow, aborting` (signal 6); depth 250 is fine. In a release build the same snippets pass or raise `RecursionError` up to depth 300,000, so this affects debug builds only (`cargo run`, a downstream `cargo test`). TS is not exposed: it runs Monty in a worker process (`DIVERGENCES.md:25`). Fix: give the dedicated thread of finding 1 an explicit stack (`std::thread::Builder::stack_size`, 16 MiB or more) and add the depth-500 snippet as a test, which today kills the test binary.

5. `harness-rs/strands-harness/src/tools/programmatic_tool_caller/run.rs:94`: `Instant::now() + timeout` panics for a large public `timeout` (`MakeProgrammaticToolCallerOptions { timeout: Some(Some(Duration::MAX)) }`). Evidence: `ptc.rs::a_huge_timeout_is_not_a_panic` fails on every call with `Other("overflow when adding duration to instant")`. Fix: `timeout.and_then(|timeout| Instant::now().checked_add(timeout))`. For the part being written now: `config/normalize.rs:589` accepts any positive `timeout` number (for example `1e300`), so the seconds-to-`Duration` conversion in `builtin_tools.rs` needs `Duration::try_from_secs_f64`.

6. `harness-rs/strands-harness/src/tools/web_fetch.rs:420`: `make_web_fetch` calls `reqwest::Client::new()`, which is documented to panic when the TLS backend or resolver cannot initialise (`reqwest-0.13.5/src/async_impl/client.rs:2516-2523`), and does so for the default `Curl` transport too, which never uses the client. Fix: build it lazily for `Direct` with `reqwest::Client::builder().build()` and return a failure as the tool's `Failed to fetch ...` text, which keeps P-852's infallible constructor.

7. `harness-rs/strands-harness/src/tools/web_fetch.rs:343,347-353,378-381`: the URL cache has expiry but no bound. `cached` skips an expired entry without removing it and nothing else removes one, so a long-lived tool keeps up to 50,000 UTF-16 units per distinct URL for good (TS `web-fetch.ts:210,243` is unbounded too). The key is the URL alone, so one tool instance shared by agents on different sandboxes serves sandbox A's fetch to sandbox B without B's network controls being consulted. Fix: `retain` unexpired entries on insert, cap the entry count, and key by sandbox identity the way `ShellCache` does.

8. Derived `Debug` prints secrets: `harness-rs/strands-harness/src/tools/web_search.rs:88-94` (`ExaConnection.api_key`, the `x-api-key` header) and `harness-rs/strands-harness/src/agent.rs:21-29` (`McpServersOption::Servers`, which after `config/options.rs:339` holds the expanded `${VAR}` values of `env` and `headers`, and is reachable through `HarnessAgentOptions`'s derived `Debug` at `agent.rs:188`). Nothing formats them today (`grep ':?}'` over non-test code finds only `programmatic_tool_caller.rs:119`), so this is latent. Fix: hand-written `Debug` impls that redact `api_key` and the values under `env` and `headers`.

Checked with no finding: `ToolAgent::call_tool` runs the batch's `ToolTask::execute` (hooks, rename and selected tool, hook cancel, middleware, span, after-hooks and retry) on a view with a throwaway `InterruptState` and the agent's shared `HookRegistry`; it does not depend on the outer batch loop, so it cannot deadlock on it, and callers are excluded from the guest's lookup, so it cannot re-enter. Guest recursion, `json.loads` depth, big-int memory, cyclic kwargs, `time.sleep`/`asyncio.sleep`, a failed `gather` with a call still in flight and 25 gathered calls behind the 10-slot semaphore all end as tool errors or results. `subagent` depth guard, resume, `pending` handling and `abort_only` match TS. `web_fetch` URL validation and sh/PowerShell quoting hold (TS has no private-address handling either) and both transports cap the body. `file_tools`, environment discovery and the shell probe go through the sandbox only; the `AGENTS.md` cap cuts on a char boundary. `interventions.rs`, `telemetry.rs` idempotence, `${VAR}` expansion against the TS regex, and lock discipline (no guard across an await in the harness crate) are sound.
