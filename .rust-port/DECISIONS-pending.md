**P-1. Commits skip the husky hook.** The pre-commit hook builds and tests strands-ts; the branch changes no TS. Options: run the hook, skip it. Choice: `git commit --no-verify` (section 9.5). Files: all commits.

**P-40. Retry shapes.** Delays are `Duration` (section 7.3): `BackoffContext { attempt: NonZeroU32, elapsed, last_delay: Option<Duration> }` (`#[non_exhaustive]`, built with `new(attempt)`, `with_elapsed`, `with_last_delay`, Phase 2 review A5), so the TS attempt and `maxAttempts` validation errors can't occur. Option structs `ConstantBackoffOptions`, `LinearBackoffOptions`, `ExponentialBackoffOptions`, `DefaultModelRetryStrategyOptions` have hand-written `Default`s with the TS defaults (1 s; 1 s/30 s/full; 1 s/30 s/x2/full; 6 attempts, exponential 4 s/240 s/full); their `bon` builders default every field to the same values, and `ConstantBackoff::default()` goes through its options (Phase 2 review A1, A2). `RetryDecision::{NoRetry, Retry { wait }}` replaces the TS `{ retry: false } | { retry: true, waitMs }`. `ModelRetryStrategy` is an `async_trait` with `name`, `compute_retry_decision(attempt_count, &Error)` and `on_first_model_attempt`; it takes the attempt and error rather than `AfterModelCallEvent` until the hook events exist (Phase 3 wires it through `AfterModelCallEvent`, the per-agent attach check and `warnOnDuplicateRetryStrategyTypes`). The TS `retryModel` body is crate-internal `retry_model`, sleeping with `tokio::time::sleep` raced against the cancel signal; tests use tokio's paused clock, so `strands` gains a `tokio` dev-dependency with `test-util`. `DefaultModelRetryStrategy` keeps its per-turn state behind a `Mutex` and measures elapsed time with `tokio::time::Instant`; `NAME` is an associated const. TS `RetryStrategy` (a type alias of `ModelRetryStrategy`) is not ported: Rust has no trait aliases. Jitter randomness comes from `fastrand` (new dependency, already in the lock file through `tempfile`), behind a crate-internal injectable `Random`. TS reference: `strands-ts/src/retry/backoff-strategy.ts:1`, `strands-ts/src/retry/default-model-retry-strategy.ts:1`. **P-44. Hook registry shape.** Section 8.5 and Appendix C. **P-45. Hooks can't fail; hook interrupts are recorded on the event.** Rust callbacks return `()` (section 8.5), so TS's "hook throws an error" paths have no equivalent and are PARITY gaps. `BeforeToolCallEvent::interrupt` and `BeforeToolsEvent::interrupt` return `Option<JsonValue>`: the stored response on resume, else they record the interrupt on the event and return `None`; after the hooks run the loop checks for duplicate names (`interrupt_names=<a, b> | duplicate interrupt names`, an `AgentError`) and stops on the interrupts. Tool interrupts keep `ctx.interrupt(..) -> Result<JsonValue, Interrupt>` (section 8.8). Files: `hooks/events.rs`, `tools/executors/mod.rs`.

**P-46. Typed hook control fields.** `Cancel { Default, Message(String) }` and `EndTurn { Default, Text(String), Content(Vec<ContentBlock>) }` replace TS's `boolean | string (| ContentBlock[])`; setters take `impl Into<..>` (`set_cancel("msg")`) plus `clear_*`. An empty message or empty block list cancels or ends nothing, as TS's falsy checks do. `resume` is `Option<InvokeArgs>`; `retry` is `bool`. Each event keeps its serializable part in a public `<Event>Data` record (exactly the TS `toJSON()` fields; `EventErrorData { message }` for `error`), which the stream yields after the hooks ran; `AgentResultEvent`'s record is `AgentResult` itself. `BeforeToolCallEventData`/`BeforeToolsEventData` carry a crate-private, unserialized `denied` flag so the printer can print TS's "(denied)" lines from records. Files: `hooks/events.rs`, `agent/stream.rs`.

**P-47. Agent stream mechanics.** The loop is an `async fn` driving an internal one-slot `Emitter`: `emit(event)` parks the loop until the consumer pulls the event, so the loop advances only as the stream is polled (TS generator semantics, #37). `AgentStream<'a>` polls the loop future and the slot; the loop's return value becomes the final `AgentStreamEvent::AgentResult` item (TS yields `AgentResultEvent` then returns the result; here they are one item). Per-tool pipelines run in spawned tasks and wait for a one-shot acknowledgement per event, so a tool advances one event per pull like a TS generator; this reproduces the TS cross-tool interleaving of the interrupt fixture. Files: `agent/stream.rs`, `tools/executors/mod.rs`.

**P-48. Tool shapes.** `Tool` is a plain trait (`name`, `description`, `tool_spec`, `stream`) returning `ToolStream` (a boxed `'static` stream of `ToolStreamItem::{Event, Outcome}`), section 8.8. `ToolError` is anyhow-like and does not implement `std::error::Error` (so the blanket `From<E: Error>` coexists with `From<Interrupt>`); `ToolError::into_outcome(tool_use_id)` is the single conversion point. `FunctionTool::builder(name, description)` returns a `FunctionToolBuilder` with `.input_schema(json)` and three finishers: `callback` (async, raw JSON, no validation, as TS `FunctionTool`), `streaming_callback` (TS async generator callbacks: every item but the last is a progress event, the last is the return value, an empty stream returns `null`), and `typed_callback::<I>` (schemars schema plus `jsonschema` validation, the TS Zod tool). Validation failures are `ToolValidationError("Tool input validation failed: <path>: <msg>; ...")`, shown to the model as `Error: ...`; Zod's error text can't be reproduced. A schema `jsonschema` can't compile skips validation. Number returns are formatted as JS `String(n)` (`1.0` becomes `1`). `ToolRegistry` keeps insertion order in an `IndexMap` and has `add`, `add_all`, `add_or_replace`, `get`, `resolve`, `remove`, `clear`, `list`, `names`, `len`, `is_empty`. Files: `strands-rs/strands/src/tools/`.

**P-49. Schema normalization.** `tools::schema_for::<T>()` runs schemars (draft 2020-12, subschemas inlined, no `$schema`) and normalizes: drops `title`, `$schema` and non-standard `format`s, strips `null` from properties that aren't required (`Option<T>` is optional, not nullable, as Zod `.optional()`), and adds `"additionalProperties": false` to object schemas that set nothing, as `z.toJSONSchema` does. Unsigned integers keep schemars' `"minimum": 0`. The `tools/tool-spec.json` fixture matches except Zod's `.min(1)`. Files: `tools/schema.rs`.

**P-50. Executors.** `ToolExecutor { Concurrent (default), Sequential }` with `From<ConcurrentToolExecutor>`/`From<SequentialToolExecutor>` unit structs, so `AgentConfig.tool_executor: Option<ToolExecutor>` covers TS's strategy strings and instances. Both executors spawn each call on a `JoinSet` task (sequential spawns one at a time); the per-call pipeline (before hooks, tool, after hooks, retries) runs in the task with `catch_unwind`, so a panicking tool becomes an error result whose text is the panic message (the TS executor's thrown-error shape, without the `Error: ` prefix) and the after hooks still run. Dropping the batch aborts the tasks. Interrupts let siblings finish (concurrent) or stop the batch (sequential), then store `pendingToolExecution`. Tool metrics and traces are recorded per call from the task's timing records; each tool trace ends on its own call (TS ends `currentTool`, which concurrent calls overwrite; logged in `ts-bugs.md`). Files: `tools/executors/mod.rs`, `telemetry/`.

**P-51. Agent views.** `LocalAgent` holds the TS-mutable state (messages, system prompt, model, aux model, registry, app and model state, id, name, description) plus crate-internal hooks, interrupt state and the current cancel signal. `ToolAgent` is an `Arc` snapshot built per batch (id, name, app state, model, aux model, cancel signal, messages `Arc<[Message]>`, registry clone, invocation context). The sandbox joins it in Phase 8 and `call_tool` with the tool caller. `InvocationState` is a cheap-clone `Arc<RwLock<http::Extensions>>` with `insert`/`get`/`remove`/`is_empty`/`ptr_eq`. Files: `agent/views.rs`, `agent/invocation_state.rs`.
