# TS bugs found while porting

Format: `file:line`, what is wrong, a minimal repro, and how Rust handles it. Facts only.

**`Uint8Array` fields are written two ways, and the index-object form corrupts on reload.** `strands-ts/src/types/messages.ts:585-589` (`ReasoningBlock.fromJSON`) keeps a non-string `redactedContent` as is, and `types/media.ts:18-41` (`encodeBase64`) treats any non-`Uint8Array` as a string for `btoa`. Stream events serialize `Uint8Array` fields with plain `JSON.stringify` (`models/streaming.ts:465`, `ReasoningContentDelta.redactedContent`), which writes an index-keyed object, while persisted blocks write base64. Repro (Node 22, built strands-ts): `ReasoningBlock.fromJSON({ reasoning: JSON.parse(JSON.stringify({ redactedContent: new Uint8Array([0, 128, 255]) })) }).toJSON()` returns `{"reasoning":{"redactedContent":"W29iamVjdCBPYmplY3Rd"}}`, the base64 of `"[object Object]"`. Fixture: `edge_cases/reasoning_redacted_uint8array_in_stream_event.json`. Rust reads base64 strings, index objects and number arrays as the same bytes and always writes base64 (P-19).

**`UnknownBlock` can be built around a known block, which reloads as that block.** `strands-ts/src/types/messages.ts:1177` (`UnknownBlock` constructor) accepts any record, including a known block's data, and `toJSON()` returns it unchanged. Repro (Node 22, built strands-ts): `Message.fromJSON(JSON.parse(JSON.stringify(new Message({ role: 'user', content: [new UnknownBlock({ text: 'hi' })] })))).content[0].constructor.name` is `TextBlock`, so the block's type changes across a save and load. Rust makes `UnknownBlock::new` crate-internal: an `UnknownBlock` comes only from deserializing data no known block matches.

**A block after unparseable tool input turns into a stale tool use.** `strands-ts/src/models/model.ts:643-652` (`streamAggregated`) resets `toolUseId` only after `JSON.parse` succeeds, and a `modelContentBlockStartEvent` without a `toolUseStart` doesn't reset it, so the next block is finalized as a tool use with the failed block's id and name and `{}` input. Repro (Node 22, built strands-ts): stream a tool-use block with input `{bad`, then a text block `after`, then `stopReason: 'maxTokens'`; the `MaxTokensError.partialMessage.content` is `[{"toolUse":{"name":"tool","toolUseId":"t","input":{}}}]` and the text is gone. Other stop reasons end in the `unable to parse tool input JSON` error, so only the max-tokens partial message shows it. Rust fixes it: the tool-use id, name and signature are cleared before parsing, so the next block stands alone (test `a_block_after_unparseable_tool_input_is_its_own_block`).

**Concurrent tool interrupts fire `InterruptEvent` for one tool only.** `strands-ts/src/tools/executors/concurrent.ts:89,126` overwrites `interruptError` with each tool's `InterruptError`, and `agent/agent.ts:2071-2085` fans out `InterruptEvent`s from that last error only, while `AgentResult.interrupts` comes from `getUnansweredInterrupts()`. Repro (Node 22, built strands-ts): a `MockMessageModel` turn with two tool uses whose `FunctionTool` callbacks each call `context.interrupt({ name: 'confirm_' + n })`, plus an `InterruptEvent` hook, gives `{"interrupts":["confirm_a","confirm_b"],"events":["confirm_b"]}`. `agent.interrupt.test.ts` ("yields one InterruptEvent per unanswered interrupt") expects the two to match. Rust collects every interrupt of the batch (P-64).

**A hook-cancelled invocation skips `MessageAddedEvent` and `AgentResultEvent` hooks.** `strands-ts/src/agent/agent.ts:1295-1316` (`_streamInvocation`, `beforeInvocationEvent.cancel`) yields `this._appendMessage(..)` directly instead of through `_invokeCallbacks`, so hooks never see the appended denial message, and it returns without the `AgentResultEvent` every other path fires. Repro: register `MessageAddedEvent` and `AgentResultEvent` hooks and a `BeforeInvocationEvent` hook setting `cancel = true`; neither fires. Rust fires both (P-74).

**Concurrent tools end the wrong local trace.** `strands-ts/src/telemetry/tracer.ts:433-440,495-500` keeps one `currentTool` slot: `startToolCallSpan` overwrites it and `endToolCallSpan` ends whatever it holds, then clears it. With two concurrent tools A and B, A's end closes B's trace and B's end finds nothing, so A's `AgentTrace` never gets an `endTime`. Repro: two slow tools in one turn with the default concurrent executor, then read `result.traces[0].children`. Rust finds each tool trace by tool use id (P-71).

**Duplicate retry strategy types warn "only the first will be used", then fail.** `strands-ts/src/retry/retry-strategy.ts:40` warns that only the first of two same-type strategies is used, but both go to the plugin registry, whose `_addAndInit` (`plugins/registry.ts:43-44`) throws `plugin already registered` for the second (same `name`) on the first invocation. The Rust port keeps both behaviours (P-80); the warning text is misleading.

**Delegation re-dispatches the child's events to the parent's hooks.** `strands-ts/src/agent/agent-delegation.ts:259-263` yields a delegate agent's own `StreamEvent`s into the parent stream, and `agent/agent.ts:1640-1644` (`_invokeCallbacks`) runs the parent's hook registry on every yielded `HookableEvent`, so a parent `MessageAddedEvent` (or `AfterToolCallEvent`, ...) hook also fires for the child's events, which already ran the child's hooks. `agent-delegation.test.ts:672` filters with `event.agent === orchestrator` to avoid counting them. Repro: the `emits exactly one assistant MessageAddedEvent` case without that filter counts the child's assistant message too. Rust yields the child's records without dispatching them to the parent's hooks.

**`AgentToolStreamer` classifies a nested delegate's result.** `strands-ts/src/multiagent/agent-tool-streamer.ts:234-239` classifies on the first `agentResultEvent` in the child stream; when the child delegates to a grandchild, the grandchild's `agentResultEvent` is surfaced first (see above), so a child that stops on a limit after its grandchild ended normally is reported as a success. Rust classifies on the child's own final result.

**`agent.cancel()` during `initialize()` is accepted and then discarded.** `strands-ts/src/agent/agent.ts:1257-1272`: `acquireLock` sets `_isInvoking` before `await this.initialize()`, so `cancel()` (`:1093-1105`) passes its idle check and aborts the current `AbortController`, but the first pass of the `while` loop calls `resetCancelState()` and replaces that controller, so the cancel has no effect and no error says so. Repro: a plugin whose `initAgent` calls `agent.cancel()` (or a timer that fires while `initAgent` awaits); the invocation runs to `endTurn`. Rust has the same outcome (the agent's handle is attached only when a pass starts, so the cancel is a no-op); an external `InvokeOptions::cancel_signal` cancelled during initialization still stops the invocation in both SDKs.

**A throttled Bedrock request is not retried unless the throttle arrives inside the stream.** `strands-ts/src/models/bedrock.ts:833-843` rethrows any error from `client.send` as is; only the in-stream `throttlingException` event becomes `ModelThrottledError` (`:2082-2086`). `retry/default-model-retry-strategy.ts` retries only `ModelThrottledError` and `ModelNetworkError`, so an HTTP 429 `ThrottlingException` on the initial `ConverseStream`/`Converse` call (after the JS SDK's own three attempts) ends the invocation. Repro: mock `send` to reject with `new ThrottlingException({ message: 'Too many tokens', $metadata: {} })`; `provider.stream(...)` rejects with `ThrottlingException`, not `ModelThrottledError`, and the agent does not retry. Rust maps `ThrottlingException` from the initial call to `ModelThrottledError` as well (P-153).

**Unknown `additionalArgs` keys are dropped silently.** `strands-ts/src/models/bedrock.ts:1048-1050` spreads `additionalArgs` into the command input; the AWS SDK serializer sends only modeled members, so a misspelled key (`additionalArgs: { requestMetadat: {...} }`) has no effect and no warning. Rust rejects such a key with an error naming it (P-154).

**A snapshot's interrupt `context` aliases the live state.** `strands-ts/src/interrupt.ts:349-361`: `InterruptState.toJSON()` returns `context: this.context` (and `pendingToolExecution`, `resumeResponses`) by reference, and `agent/snapshot.ts:106-109` puts that object into the snapshot unchanged. A snapshot taken at `BeforeInvocationEvent` of a resume therefore loses the sub-agent turn when the resumed `AgentAsTool` later runs `delete turns[toolUseId]` (`multiagent/agent-tool-streamer.ts:357`). Repro: the conformance generator's `subAgentInterruptRun` writes `snapshots/agent_sub_agent_resume_with_context.json` with `subAgentInterruptedTurns: {}` although its description says the context still holds the child turn. Rust copies the state into the snapshot; the conformance test checks the turn is present and compares the rest with the fixture.

**Chat Completions parallel tool-call deltas interleave across content blocks.** `strands-ts/src/models/openai/chat-adapter.ts:420-441`: each `tool_calls` delta is mapped as it arrives; a delta with `id` and `function.name` emits `modelContentBlockStartEvent`, and any delta with `function.arguments` emits `toolUseInputDelta` immediately, whatever its `index`. Repro: stream chunks `[{index:0,id:'a',function:{name:'x',arguments:''}}]`, `[{index:1,id:'b',function:{name:'y',arguments:''}}]`, `[{index:0,function:{arguments:'{"p":1}'}}]`, then `finish_reason: 'tool_calls'`: the events are start(x), start(y), delta('{"p":1}'), stop, stop, so `streamAggregated` attaches x's arguments to y (or fails to parse). The same path opens a tool block while a text block is still open (`handles messages with both text and tool calls` shows start(text), deltas, start(tool) before the text stop). Rust gathers deltas by index and emits each call whole, in index order, after closing the text block (P-204).

**Chat Completions drops tool calls whose arguments arrive before the id.** Same lines: a delta without `id`/`name` for an index that has not started emits `toolUseInputDelta` with no open tool block. Rust buffers the fragments under the index and emits them once the call has an id and name; a call that never gets both is skipped with a warning.

No TS bugs found while porting Phase 9 items 1-4 (MCP client, legacy SSE transport, item-3 features, `loadServers`).

**A Responses stream that ends without a terminal event reads as a complete answer.** `strands-ts/src/models/openai/responses-adapter.ts:671-706` with `strands-ts/src/models/openai/model.ts:319-331`: when the SSE stream ends cleanly with no `response.completed`, `response.incomplete` or `response.failed`, `finalizeResponsesStream` still yields `modelMessageStopEvent` with `endTurn`, so a truncated response is returned as finished and the aggregator's "Stream ended without completing a message" check never runs. Repro: a mocked stream of `response.created` and one `response.output_text.delta`, then end of stream; TS yields the text and `stopReason: 'endTurn'`. Rust sets a flag on `response.completed`/`response.incomplete` and, when neither arrived, fails the stream with `ModelError` "Stream ended without completing a message" (the aggregator's text).

**`buildShellEnvPrefix` and `shellQuote` are documented for implementers but not exported.** `strands-ts/src/sandbox/posix-shell.ts:47-63` tells `PosixShellSandbox` subclasses to prepend `buildShellEnvPrefix` (or call `validateEnvKeys`) in `executeStreaming`, or `options.env` has no effect, but `sandbox/index.ts:1-4` and `index.ts:403-413` export only `Sandbox`, `PosixShellSandbox`, the types and `LANGUAGE_PATTERN`. Repro: `import { buildShellEnvPrefix } from '@strands-agents/sdk/sandbox'` fails to resolve; the in-repo fixture (`__fixtures__/test-sandbox.node.ts:1-2`) imports it by relative path. Rust exports `build_shell_env_prefix`, `validate_env_keys` and `shell_quote` from `strands::sandbox` (P-262).

**An empty context `Choice` passes `makeSubagent` validation and yields an empty enum.** `strands-ts/src/vended-tools/subagent/subagent.ts:132-138` validates only the context modes the `Choice` lists, and `buildSchema` (`subagent.ts:177-190`) renders `context` without the empty-options check `_toSchemaProperties` applies to the other axes (`multiagent/spec.ts:242-246`). Repro: `makeSubagent({ context: new Choice([]) }).toolSpec.inputSchema.properties.context.enum` is `[]`, a parameter no value satisfies, while `makeSubagent({ model: new Choice([]) })` throws `model: new Choice([]) offers no options; ...`. Rust mirrors TS (P-281).

**Tool-result truncation drops the message metadata.** `strands-ts/src/conversation-manager/sliding-window-conversation-manager.ts:448-452` rebuilds the truncated message from `role`, `content` and `trackingId` only, so its `metadata` (usage, metrics, custom keys other than `pinned`; pinned messages are skipped) is lost on every overflow truncation. Repro: a user tool-result message with `metadata: { custom: { source: 'x' } }` and a 500-char result, then `reduce({ agent, model, error: new ContextWindowOverflowError('o') })`; `messages[0].metadata` is `undefined`. The Rust port mirrors it (P-96).

**`compressionThreshold: NaN` passes validation.** `strands-ts/src/conversation-manager/conversation-manager.ts:131` checks `threshold <= 0 || threshold > 1`, both false for `NaN`, so `{ compressionThreshold: NaN }` is accepted and proactive compression silently never fires (`ratio >= NaN` is false). The Rust port rejects it with the range error (P-96).

**`mcp_router` `call_tool` errors reach the model with a doubled `Error: ` prefix.** `strands-ts/src/vended-tools/mcp-router/mcp-router.ts:286-292` rethrows the text of the ad-hoc `McpTool`'s error result as `McpRouterToolError`; when the MCP call itself threw (abort, transport failure, protocol error), that result came from `createErrorResult` (`strands-ts/src/tools/tool.ts:201-210`), whose text is already `Error: <message>`, and the tool factory wraps the rethrown error again. Repro: `call_tool` on a connection whose call is cancelled through the invocation signal; the tool result text is `Error: Error: The operation was aborted` (or the cancel message). A server `isError` result (`boom`) is not affected. Rust mirrors TS (the router error text is `Error: <message>`).

**A generic namespace view with a trailing-slash prefix lists truncated keys.** `strands-ts/src/storage/storage.ts:193-200` (`namespace`) builds `p` from `normalizePrefix(prefix)`, which keeps a trailing `/`, and then appends another, so `namespace(storage, 'prefix/')` uses `prefix//`. Writes normalize to `prefix/key`, but `list` slices `p.length` (8) characters off each key. Repro (Node 22, built strands-ts): `const v = namespace(new InMemoryStorage(), 'prefix/'); await v.write('key', bytes); await v.list('')` returns `['ey']`. `InMemoryStorage.namespace` strips the trailing slash (`in-memory-storage.ts:143`) and doesn't have the problem. Rust strips the trailing slash in the generic view too, and strips the prefix by match rather than by length (`storage::tests::a_trailing_slash_prefix_lists_whole_keys`).

**Sandboxed `LocalFileStorage` writes skip the search strategy's `index`.** `strands-ts/src/storage/local-file-storage.ts` `write` returns right after `sandbox.writeFile` (the sandbox branch), so `searchStrategy.index` runs only for host writes, while `search` still delegates to the strategy for both. Repro: `new LocalFileStorage(dir, { sandbox, searchStrategy: { index: spy, search } }).write('a', bytes)` never calls `spy`. Rust keeps the TS behaviour (no index call for sandboxed writes) so a strategy sees the same calls in both SDKs.

No new TS bugs from the Phase 8 fixes.

**`pin_context` advertises `action` as required although it has a default.** `strands-ts/src/context-manager/modes/agentic/agentic-context.ts:206` declares `action: z.enum(['pin', 'unpin']).default('pin')`; `z.toJSONSchema` (output mode, used by `tools/zod-utils.ts:12`) puts `action` in `required`, so the model is told to always send it, while the tool's Zod parse accepts input without it. Repro: `z.toJSONSchema(pinContextTool's schema).required` is `["select", "action"]`, and `pinContextTool.invoke({ select: 2 })` succeeds. Rust sends the same schema and accepts input without `action` (P-319).

**The skill location is always `<path>/SKILL.md`, also for a skill loaded from `skill.md`.** `strands-ts/src/vended-plugins/skills/agent-skills.ts:66` and `skill.ts:47` accept a lowercase `skill.md` when `SKILL.md` is absent, but `_generateSkillsXml` (`agent-skills.ts:477`) and `_formatSkillResponse` (`agent-skills.ts:507`) build the location as `${skill.path}/SKILL.md`. Trigger: a skill directory holding only `skill.md`. Behaviour: the system prompt's `<location>` and the tool response's `Location:` name a file that does not exist on a case-sensitive file system. Rust mirrors TS (same texts).

**A bare `SKILL.md` path source never loads in strict mode.** `strands-ts/src/vended-plugins/skills/agent-skills.ts:295-297` loads a path ending in `skill.md` with `skillDir = '.'` when the path has no `/`, and `validateSkillName` (`skill.ts`) then compares the skill name with `basename('.')`, which is `.`. Trigger: `new AgentSkills({ skills: ['SKILL.md'], strict: true })`. Behaviour: every skill fails with `skill name does not match parent directory name` (a warning without `strict`), and the skill's `path` is `.`. Rust mirrors TS.

**`FileMemoryStore.add` drops a second heading-less entry written in the same millisecond.** `strands-ts/src/vended-memory-stores/file-memory-store/store.ts:270` falls back to `entry-${Date.now()}.md` when the first line has no slug characters, and `:283` keeps only the existing content when the new entry has no lines after the first. Two such entries in one millisecond share the key, so the second is treated as an append with no new facts and is discarded while `add` resolves with the key. Repro (built SDK, `Date.now` pinned): `await store.add('!!!'); await store.add('???')` leaves one file containing `!!!`. Rust mirrors the behaviour. A fix would make the fallback key unique (a counter or random suffix).

**`ModelExtractor` forwards non-object `metadata` from the model.** `strands-ts/src/memory/extraction/model-extractor.ts:161` copies `record.metadata` whenever it is not `undefined`, so `[{"content": "x", "metadata": "oops"}]` reaches `store.add(content, "oops")` although the parameter is typed `Record<string, JSONValue>`. Rust keeps only object metadata (listed in DIVERGENCES).

**`search_memory` accepts any number for `maxSearchResults`.** `strands-ts/src/memory/memory-manager.ts:634` declares `z.number().optional()`, so negative and fractional limits are forwarded to every store's `search`. `z.number().int().positive()` would match what stores expect.

**`CedarAuthorization` leaks a call count when the context enricher throws.** `strands-ts/src/vended-interventions/cedar/cedar.ts` `beforeToolCall` calls `_incrementCallCount` and then `this._contextEnricher(..)` inside the `isAuthorized` argument; an enricher that throws leaves the count incremented although the call was never evaluated, so with `onError: 'proceed'` or `'deny'` a rate-limit policy (`context.session.call_count < N`) is used up by failed calls. The deny and failure paths call `_decrementCallCount`; the throw path doesn't. Rust keeps the TS order and behaviour (P-415).

**The `HumanInTheLoop` approval prompt loses the classifier reason on resume.** `strands-ts/src/vended-interventions/hitl/hitl.ts` `_requiresApproval` returns `{ requiresHumanInTheLoop: true }` with no reason for a tool use id it has already classified, so when the agent resumes after an interrupt the `Confirm` prompt is rebuilt without ` — <reason>`. The interrupt id doesn't include the prompt, so the stored response still matches; only the prompt text differs between the first pass and the resume. Rust does the same.

**A hook that throws at a tool gate still runs the next model call.** `strands-ts/src/agent/agent.ts:1516-1532` (`_streamCore` cleanup) drains `_stream()` after the error, and the `finally` of `executeTools` (`agent.ts:2834-2843`) yields `AfterToolsEvent` and lets the loop run on. Repro (Node 22, built strands-ts): a model that answers a tool use and then `Done`, and a `BeforeToolCallEvent` hook (or an intervention handler with the default `onError: 'throw'`) that throws `new Error('crash')`; `agent.invoke('hello')` rejects with `crash`, yet the model is called a second time and `agent.messages` ends as `[user "hello", assistant "Done"]`. Rust stops at the failing gate: one model call, `[user "hello"]`, the same error (P-648).

**Intervention gates run on the pass an earlier hook pauses, and again on resume.** `strands-ts/src/hooks/registry.ts:90-100` keeps calling the remaining callbacks after one raises an `InterruptError`, so when a `BeforeToolCallEvent` hook registered before the interventions interrupts, every intervention handler's `beforeToolCall` still runs on that pass and runs again when the agent resumes. Effects: `CedarAuthorization` counts the call twice (a policy with `context.session.call_count <= 1` denies the first call after the resume), and `HumanInTheLoop` with an `ask` callback asks twice. Rust does the same.

**The harness `edit` tool expands `$` patterns in `new_str`.** `harness-ts/src/tools/file-tools.ts:221` calls `content.replace(input.old_str, input.new_str)` with a string replacement, so `$&`, `` $` ``, `$'` and `$$` in `new_str` are replacement patterns: `new_str: "cost: $$5"` writes `cost: $5`, and `"$&"` writes back `old_str`. The tool describes `new_str` as "Replacement text." Rust writes `new_str` literally (P-850, `edit_inserts_the_replacement_literally`).

**The harness `edit` tool accepts an empty `old_str` on some files.** `file-tools.ts:213` counts occurrences with `content.split(input.old_str).length - 1`; for an empty `old_str` that is the file's UTF-16 length minus one, so a two-character file reports one occurrence and `new_str` is inserted at the start, an empty file reports -1 and takes the same path, a one-character file reports "did not appear verbatim", and a longer file reports "appears N times". Rust does the same.

**The harness `read` tool reads a negative `limit` as an end offset.** `file-tools.ts:141-142` passes `start + count` to `lines.slice`, and the schema is `z.number()` with no lower bound, so `limit: -1` returns every line but the last and `limit: 0` reports `[File has N lines; offset undefined is past the end.]`. Rust does the same.

**`web_fetch` can cut a surrogate pair.** `harness-ts/src/tools/web-fetch.ts:131` truncates with `text.slice(0, MAX_CHARS)`, which counts UTF-16 code units, so a page whose 50,000th unit is the first half of an astral character ends in a lone surrogate. Rust drops that character (a Rust string cannot hold half of one).

**The harness `subagent` tool does not forward the invocation context.** `harness-ts/src/tools/subagent.ts:687` calls `child.stream(prompt, { invocationState, cancelSignal })` under the comment "Forward cancel signal + invocation state (mirrors the SDK's AgentAsTool)", but `strands-ts/src/agent/agent-as-tool.ts:228-232` and `strands-ts/src/vended-tools/subagent/subagent.ts:277` also pass `invocationContext`, so a harness child runs as a request of its own rather than inside the parent's. Found by reading the code, not by running it. Rust follows the harness TS and passes only the invocation state and the abort signal (P-896).
