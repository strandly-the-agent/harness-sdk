# Common rules for the Phase 12 review fix tracks

Read `.rust-port/briefs/run5-common.md` first (it names `run4-h12-common.md` and `run3-common.md`); everything there applies, with these differences.

- You fix verified review findings from the Phase 12 review gate. The reports are in `.rust-port/reviews/` (or `/mnt/workspace/reviews/` when your brief says so); each finding has `file:line`, the evidence and a proposed fix. Read the whole finding, reproduce it (the correctness reviewer's probes are in `.rust-port/reviews/phase12-review-correctness-probe/`), then fix it with a regression test named for the behaviour. The reviewer's proposed fix is a suggestion: if the TS source at the pin (`/tmp/ts-spec`) shows something else is right, do that and say why.
- Every finding gets a disposition. Fix every verified finding. Where you disagree with a finding, or a fix would contradict a binding decision of PROMPT.md section 6 or the rules of section 7, don't change the code: record why, with evidence. Where a TS behaviour is itself wrong, fix it in Rust (decision #74), and stage a `ts-bugs.md` entry and a `divergences.md` row; never change a cross-SDK wire or persisted format.
- One commit per finding (`fix(harness): ...` or `fix(strands): ...`), each compiling with its tests passing. SDK changes (`strands-rs/`) are allowed where the finding is in the SDK or cannot be fixed without one: smallest change, own commit, pending decision.
- Stage, in `.rust-port/staging/<track>/`: `dispositions.md` (a table `| finding | disposition | commit |`, one row per finding of your brief; facts only, no severity labels; write the row right after the commit), `decisions.md`, `ts-bugs.md`, `divergences.md` (rows for `harness-rs/docs/DIVERGENCES.md`, or say in the row's first column when it belongs in `strands-rs/docs/DIVERGENCES.md`), `parity.md` only if a PARITY row changes.
- Other fix tracks run at the same time on other files (your brief lists who owns what). Edit only your files; if a fix needs a line in a file another track owns, keep it to that line, in its own commit, and list it in the report.
- Before your last commit run, for each crate you touched: `cargo fmt --all --check`, `cargo clippy --locked -p <crate> --all-targets --all-features -- -D warnings`, the same with `--no-default-features`, `cargo test --locked -p <crate> --all-features`, the same with `--no-default-features`, and `RUSTDOCFLAGS="-D warnings" cargo doc --locked -p <crate> --all-features --no-deps`. For `strands` the test run is long: run the touched modules' tests and the integration tests that cover them (`--test <name>`), then the whole crate once at the end if time allows; say in the report exactly what you ran.
- Report (under 350 words): one line per finding (fixed with commit and test name, or not fixed with the reason), P numbers used, edits outside your files, what you ran, what is left.
