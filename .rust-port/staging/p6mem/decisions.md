**P-350. Memory module layout and the `MemoryStore` trait.** `strands::memory` mirrors TS `src/memory/` (`types`, `memory_manager`, `extraction/{types, triggers, coordinator, resolve_extraction_config, model_extractor}`) and `strands::vended_memory_stores::file_memory_store` mirrors `vended-memory-stores/file-memory-store`. TS marks `add`, `addMessages`, `initialize` and `getTools` optional and the manager tests `typeof store.add === 'function'` at construction. An object-safe Rust trait can't omit a method, so `MemoryStore` has `supports_add()` and `supports_add_messages()` (default `false`) beside `add` and `add_messages` (default: an error naming the store); `initialize` defaults to `Ok(())` and `get_tools` to none. TS `add` and `addMessages` return `Promise<unknown>` and no caller reads the value, so the trait methods return `Result<()>`; `FileMemoryStore::add` (inherent) returns the key, as TS does. TS reference: `memory/types.ts:66-180`. Files: `src/memory/types.rs`, `src/vended_memory_stores/file_memory_store.rs`.

**P-351. TS unions in the memory config.** `searchToolConfig`, `addToolConfig` and `injection` are `boolean | Config`; Rust has `MemorySetting<T>` (`Off`, `On`, `Config(T)`) with `From<bool>` and `From<Config>`, so the builder takes `false`, `true` or a config; `None` is the TS default (search on, add off, injection on). `extraction?: boolean | ExtractionConfig` is `Option<ExtractionConfig>` (`Some(ExtractionConfig::default())` is `true`), likewise `FileMemoryStoreConfig::extraction`. `ExtractionConfig::trigger` is a list (TS also takes one trigger). `MemoryAddToolConfig::stores` takes names (TS also takes store instances and reads their `name`). `MemoryInjectionConfig::query` and `format` return `Result`, because TS callbacks may throw and a throw skips injection. TS reference: `memory/types.ts:182-291`, `memory/extraction/types.ts:140-157`. Files: `src/memory/types.rs`, `src/memory/extraction/types.rs`.

**P-352. Extraction runs on spawned tasks.** TS chains one promise per store (`_chains`) and never awaits it in the hook. Rust keeps the tail of each store's queue as a `futures::future::Shared` future, chains the next save behind it, and drives it with `tokio::runtime::Handle::try_current().spawn(..)` instrumented with `in_current_span` (section 11 items 35 and 42d); outside a runtime the save stays queued until `flush`. `flush` queues a save for every store (bypassing backoff, as TS does) and waits until no save was queued while it waited (a generation counter replaces the TS promise-identity check). Stores are addressed by index in the coordinator, since Rust has no object identity for a `Map` key. The default model is `agent.aux_model()` read when the manager attaches, as TS documents. TS reference: `memory/extraction/coordinator.ts`. Files: `src/memory/extraction/coordinator.rs`.

**P-353. Injection helper inside `memory` until `injection` lands.** The `p6is` track owns TS `src/injection/`. Memory needs `InjectionTrigger`, `InjectionContext`, `createInjectionMiddleware`, `isUserTurn`, `foldIntoLastUserMessage`, `escapeXmlText` and `escapeXmlAttr`. `src/memory/injection.rs` holds the minimum: public `InjectionTrigger` (`UserTurn`, `EveryTurn`, `Predicate`), `InjectionContext` and `InjectionPredicate`, re-exported from `strands::memory` as TS `memory/index.ts` re-exports them, and crate-internal `create_injection_middleware`, `is_user_turn`, `fold_into_last_user_message`, `escape_xml_text`, `escape_xml_attr`. When `strands::injection` is merged, `memory` should import from it, delete this file, and re-export the three public types from there. TS reference: `injection/message-injection.ts`, `injection/types.ts`, `injection/xml.ts`. Files: `src/memory/injection.rs`.

**P-354. Agent wiring for memory: the shared-file edits.** `agent/config.rs`: the `memory_manager: Option<MemoryManagerSource>` key and `MemoryManagerSource` (`Manager(MemoryManager)` or `Config(Box<MemoryManagerConfig>)`, with `From` for both, as TS takes `MemoryManager | MemoryManagerConfig`). `agent/agent.rs`: the manager is built in `Agent::new` (a config error fails construction, as the TS constructor throws), joins `registration_order` after delegation and before the context manager, `Agent::memory_manager()`, and `shutdown()` flushes memory after finishing an abandoned run. `agent/mod.rs`: exports `MemoryManagerSource`. `lib.rs`: `pub mod memory; pub mod vended_memory_stores;`. `MemoryManager` is a cheap handle (`Arc` inside), so the agent and the caller share one manager. TS reference: `agent/agent.ts:275, 588-592, 700, 1181`. Files: those four.

**P-355. Memory telemetry waits for Phase 10.** TS wraps search, add, inject and extract in tracer spans and hands the extractor a `tracer`. The Rust tracer has no memory spans yet, so `ExtractorContext` has `default_model` and `invocation_context` only (it is `#[non_exhaustive]`), and `memory-tracing.test.ts` is 0/17. Phase 10 adds the spans around the same call sites. TS reference: `memory/memory-manager.ts`, `telemetry/tracer.ts`. Files: `src/memory/memory_manager.rs`, `src/memory/extraction/{coordinator, model_extractor}.rs`.

**P-356. Memory errors.** Every TS `throw new Error('MemoryManager: ..')` is `Error::Other` with the same text (P-23). TS `add` throws an `AggregateError` naming the failed stores, and the add tool flattens nested aggregates into the store errors; Rust keeps the per-store reasons in a private `AddFailure` so the tool error reads the same (`failed to add N of M entries: <reason>; <reason>`), and the public `add` returns one error with the TS message. `MemoryManager::flush` returns `()`: saves log their failures and never reject, as in TS. TS reference: `memory/memory-manager.ts:520-700`. Files: `src/memory/memory_manager.rs`.

**P-357. `FileMemoryStore` details.** The deprecated `search` option is not ported (decision #24). Slugs and merges use the JavaScript whitespace set (`\s`, `trim`), the fallback key is `entry-<unix ms>.md` from `SystemTime`, writes to one key are serialized with a per-key `tokio::sync::Mutex` (TS chains promises per key), and `resolve_namespace` follows TS `resolveNamespace` (already namespaced, else the backend's own `namespace`, else the generic view). The search path log is written once the backend has answered, because Rust learns that a backend has no search from the `None` it returns. TS reference: `vended-memory-stores/file-memory-store/store.ts`. Files: `src/vended_memory_stores/file_memory_store.rs`.

**P-358. The read-only memory view lives in `strands`, hidden.** The recall-only view is harness-ts `toReadOnly` (`harness-ts/src/memory.ts:101-110`), not a strands-ts export, but the Phase 6 scope lists it and the harness crate needs it. `strands::memory::read_only_view(store)` is `#[doc(hidden)]` (the AGENTS.md rule for items another workspace crate needs): it keeps `name`, `description`, `max_search_results`, `search` and `initialize`, reports `writable() == false`, and drops `add`, `add_messages`, `extraction` and `get_tools`.
