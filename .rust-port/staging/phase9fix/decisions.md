**P-257. MCP auth headers and client-credentials renewal.** Phase 9 review (correctness 7, 8). With `auth` or `auth_provider`, a user `Authorization` header went out next to the bearer token (`reqwest` appends); and a client-credentials token was granted once per connection, so after expiry `rmcp`'s refresh (client-credentials responses carry no refresh token) failed and requests went out unauthenticated until `connect(true)`. TS sets the token with `headers.set("Authorization", ..)`, and its non-interactive provider runs the grant again on a 401. Choice: with `auth` or `auth_provider`, `authorization` is dropped from the custom headers, so the token wins. The url-configured client with `auth` uses a private `StreamableHttpClient` (`mcp::auth::ClientCredentialsClient`) around the granted `AuthClient`: before each request it takes the stored token, or runs the grant again when `rmcp` reports none usable; on a 401 it runs the grant again (once per rejected grant, shared by concurrent requests) and retries once. A freshly granted token is used as granted, without `rmcp`'s 30-second expiry margin, so a server issuing tokens shorter than 30 s still works.
