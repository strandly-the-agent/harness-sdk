**P-720. `telemetry::get_tracer` and `telemetry::get_meter` (TS `getTracer`, `getMeter`).** Under `otel`, `get_tracer() -> opentelemetry::global::BoxedTracer` is `global::tracer(service_name)` and `get_meter() -> opentelemetry::metrics::Meter` is the global provider's meter scoped to the service name, the same scope the agent's own instruments use. Both are no-ops until a provider is registered, as in TS. A span started from `get_tracer()` inside an agent's `tracing` span parents under it once `setup_tracer` (or the application's own `tracing_layer`) is installed (the API review's `get_tracer_feasible.rs`). Files: `strands-rs/strands/src/telemetry/config/setup.rs`, `telemetry/mod.rs`. Review finding api-1.

**P-721. What the `setup_tracer` subscriber exports.** `tracing_layer` turns off the layer's own attributes (`with_location(false)`, `with_threads(false)`, `with_tracked_inactivity(false)`, `with_target(false)`), so an agent span carries only the attributes TS sets, on both the `setup_tracer` path and an application's own subscriber. The subscriber `setup_tracer` installs adds a per-layer filter, `metadata.is_span() && level <= INFO`: the agent's spans are `info_span!`, the `debug`/`trace` spans of dependencies (HTTP and AWS clients) are not exported, and `tracing` log lines don't become span events or set a span's error status, as TS `logger` calls never do. The SDK's own span events are unaffected (they go through `OpenTelemetrySpanExt::add_event`). An application that wants more builds its own subscriber with `tracing_layer`, which carries no filter. Files: `strands-rs/strands/src/telemetry/config/setup.rs`. Review finding api-2.
