**P-870. `ToolAgent::call_tool` exists now (SDK change, needed by the harness).** PROMPT.md section 9 and decision #62 describe `ToolAgent::call_tool`, but the SDK had no such method, and `programmatic_tool_caller` cannot gate inner calls without it. Added `pub async fn call_tool(&self, name: &str, input: JsonValue, invocation_state: InvocationState) -> Result<ToolCallOutcome>` and `#[non_exhaustive] pub enum ToolCallOutcome { Result(ToolResultBlock), Interrupt(Interrupt), Cancelled }` (`strands::types::agent`). It reuses the executor's `ToolTask::execute` over a channel of its own (`tools/executors/executor.rs::call_tool`), so the call gets the whole per-tool pipeline: `BeforeToolCallEvent` hooks and interventions, hook cancel, tool substitution and rename, the `ExecuteToolStage` middleware, the tool span, `AfterToolCallEvent` hooks and their retry. Stream updates are dropped, nothing is routed to the background, and the call runs on a view with a throwaway interrupt state, so an interrupt is returned and never recorded. `Cancelled` is returned when the agent's cancel signal is already set. The tool use id is `call_<uuid v7>`. The invocation state is an argument because it lives on `ToolContext`, not on the agent view; `ToolAgentInner` gained the `HookRegistry` and `LocalTelemetry` handles. Files: `src/types/agent.rs`, `src/tools/executors/executor.rs`, tests in `src/types/agent/tests.rs` (`call_tool` module, 5 cases).

**P-871. `InvocationState::detached()` (SDK change).** A copy with its own storage. TS hands an inner call `{ ...parent.invocationState }` so it cannot change the parent's state; Rust's `InvocationState` is a shared handle and had no public copy. One test in `src/types/agent/tests.rs`.

**P-872. `monty-types` is a direct dependency of `strands-harness`.** `monty` 1.5 does not re-export its boundary types (`MontyObject`, `MontyException`, `ResourceLimits`, `PrintWriter`, ..); they are in `monty-types`, which was already in `Cargo.lock` through `monty`. Added `monty-types = "1.5"` to `[workspace.dependencies]`. No new compiled crate.

**P-873. Programmatic tool callers are recognised by name.** TS keeps a `WeakSet` of caller tool objects. The Rust `Tool` trait has no identity or downcast, so the module keeps a process-wide set of every name a caller was made with, and no registry tool with such a name is exposed to the code. A tool that is not a caller but shares a name with a caller made elsewhere in the process is hidden too.

**P-874. Shape of the public API.** `make_programmatic_tool_caller(MakeProgrammaticToolCallerOptions) -> FunctionTool` and `programmatic_tool_caller() -> FunctionTool` (TS exports a constant; a function, as `strands::vended_tools::sleep()`). `MakeProgrammaticToolCallerOptions { allowed_tools: Option<Vec<String>>, name: Option<String>, description: Option<String>, timeout: Option<Option<Duration>> }`: `timeout` is TS `timeoutMs?: number | null`, with `None` the 900 s default and `Some(None)` no ceiling. `LIMITS`, `MAX_CONCURRENT_TOOL_CALLS` and `Output` (TS exports them for its tests) are `pub(crate)`.

**P-875. How the code runs.** `MontyRun` from the `monty` crate, in this process, every interpreter step on `spawn_blocking`. VM limits: `max_feed_duration` 60 s (lowered to the wall-clock timeout when that is shorter), `max_memory` 256 MiB, and the suspension budget (1000), which Monty leaves to the host: the run is aborted with an exception the code cannot catch. Names resolve through Monty's name lookup and every function call is checked against the exposed set again (Monty suspends with a function call for any unknown global that is called), so a tool outside `allowed_tools` raises `NameError`. Every OS call gets Monty's no-handler answer (`PermissionError`, or `ModuleNotFoundError` for an import). A parent cancel is answered at once; a step that is still computing is left to run into the VM duration limit on its blocking thread.

**P-876. Test seams.** `pub(crate) fn make_programmatic_tool_caller_with(options, inner: InnerCaller, limits: Limits)`; `InnerCaller` is the inner-call function (`ToolAgent::call_tool` in the tools the crate hands out) and `Limits` the VM limits, so tests lower a limit without a process-wide mutable (TS mutates the exported `LIMITS`).
