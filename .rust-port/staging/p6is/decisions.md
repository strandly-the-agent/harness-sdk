**P-380. Injection module shape and names; P-380 adds to the P-15 name map.** TS `injection/` exports three types from the package (`InjectionConfig`, `InjectionTrigger`, `InjectionContext`) and keeps the engine `@internal`. Choice: `strands::injection` is a public module with `InjectionTrigger::{UserTurn, EveryTurn}` (`Default` is `UserTurn`), `InjectionContext { messages: Vec<Message>, app_state: StateStore, agent: ToolAgent }` (TS `agent: LocalAgent`; a middleware context holds a `ToolAgent`) and `InjectionConfig` (`new`, `with_trigger`, `with_trigger_fn`; the TS union `InjectionTrigger | predicate` is the private `Trigger`). Crate-internal, for `ContextInjector` and the memory manager: `Trigger::{Named, Predicate}` with `fires(&InjectionContext)` (TS `resolveTrigger(..)(context)`), `is_user_turn`, `fold_into_last_user_message(Vec<Message>, &str) -> Folded { messages, appended }` (takes the call's messages by value instead of copying them), `InjectionMiddlewareOptions { trigger, render_content }`, `RenderContent` (`Arc<dyn Fn(InjectionContext) -> BoxFuture<'static, Result<Option<String>>>>`) with the `render_content(closure)` boxing helper, `apply_injection(&opts, InvokeModelContext) -> InvokeModelContext` (the handler body, callable from tests) and `create_injection_middleware(opts) -> Middleware<InvokeModelStage>`, plus `escape_xml_text` and `escape_xml_attr`. The module carries one `allow(dead_code, unused_imports)` because the fold engine and the XML helpers have no caller until the memory manager lands; remove it then. TS reference: `injection/{types, message-injection, xml}.ts`. Files: `src/injection.rs`, `src/injection/`.

**P-381. A trigger predicate returns `bool`.** TS wraps a user predicate so a throw logs `injection trigger threw; skipping injection` and skips. A Rust predicate is `Fn(&InjectionContext) -> bool` and has no error to report, so that branch and its log line don't exist; a panic is not caught. The TS case `fails open (returns false, logs) when a custom predicate throws` has no Rust equivalent. `render_content` is fallible and fails open with the TS log text (`reason=<..> | injection renderContent threw; skipping injection`).

**P-382. `ContextInjector` writes the history through the `ToolAgent` edit slot.** TS `_inject` assigns `context.agent.messages[last]` inside an `InvokeModelStage` Input handler. A Rust handler holds a `ToolAgent` snapshot, so the injector reads `ToolAgent::current_messages()` (which includes an earlier injector's write on the same call) and calls the existing crate-internal `ToolAgent::replace_messages`; `invoke_model_with_middleware` (`agent/run.rs`) now keeps the `ToolAgent` it built the context from and applies `take_history_edit()` before each item the chain yields and once after the chain, including when the model call fails, so a retry finds the block and doesn't render again. The write therefore lands before the hooks of the call's first stream event rather than before the model is called; a Wrap handler reading `context.agent().messages()` on the same call sees the history without the block. API: `ContextInjectorConfig::new(render)` with `with_name`, `with_trigger`, `with_trigger_fn` (TS `ContextInjectorConfig` has a required callback, so it is a constructor plus setters rather than a struct literal), `ContextInjector::new(config)`; the module re-exports `InjectionContext` and `InjectionTrigger` as TS `context-injector/index.ts` does. Module: `strands::vended_plugins::context_injector` (TS `vended-plugins/context-injector/`), mirroring `vended_tools`. Files: `src/vended_plugins.rs`, `src/vended_plugins/context_injector.rs`, `src/agent/run.rs`.

**P-383. Skills API mapping.** Module `strands::vended_plugins::skills` (private `skill` and `agent_skills`, re-exported). `SkillConfig` is a struct-literal config with a `bon` builder; `Skill` has private fields with getters, `metadata` is a `JsonObject`, `path` is a `String` (sandbox paths are strings). The TS option bags of `fromContent` (`{ strict, path }`) and `fromFile`/`fromDirectory`/`fromUrl` (`{ strict }`) are one `SkillOptions { strict: bool, path: Option<String> }`; only `from_content` reads `path`. `from_file` and `from_directory` use `std::path::absolute` for Node `resolve` (no `..` normalization, no cwd change). `SkillSource::{Path(String), Skill(Skill)}` with `From<&str>`, `From<String>`, `From<Skill>` (TS `string | Skill`; an `https://` string is a URL). `AgentSkillsConfig { skills, max_resource_files, strict, state_key }`. `AgentSkills` is `Clone` (shared state) so a caller keeps a handle after giving the plugin to the agent: `get_available_skills(agent_id: Option<&str>)`, `set_available_skills(Vec<SkillSource>)`, `get_activated_skills(app_state: &StateStore)`. TS keys per-agent skills by the agent object (`WeakMap`) and takes the agent in both getters; Rust code holds an `Agent`, a `LocalAgent` or a `ToolAgent` depending on where it runs, so the per-agent map is keyed by agent id and the activated-skills getter takes the app state. Two agents with the same id sharing one plugin instance share the entry (the last one initialized wins). The `skills` tool is built with the crate's `schema_tool` and the JSON schema zod emits (checked against the built TS SDK). Files: `src/vended_plugins/skills.rs`, `src/vended_plugins/skills/`.

**P-384. `SKILL.md` frontmatter is parsed with a YAML subset, without a YAML dependency.** TS uses the `yaml` package and, when it throws, retries after quoting values that hold a colon. The workspace has no YAML crate and adding one is a shared-manifest and `deny.toml` change outside this track. Choice: a small parser for what a frontmatter holds: a top-level mapping of plain, single-quoted and double-quoted scalars (`null`/`~`, booleans, integers and floats are typed; a plain scalar ends at ` #`), flow sequences of scalars, block sequences of scalars, and one level of nested mapping (`metadata:`). A plain scalar keeps everything after `key: `, so `description: Use when: ...` yields the string the TS fallback produces, without the `YAML parse failed, retrying with colon-quoting fallback` warning. Not supported: block scalars (`|`, `>`), multi-line plain scalars, anchors and tags, nested sequences or deeper mappings; such lines are skipped rather than rejected, where the `yaml` package would parse them or throw. Revisit with a YAML crate if the owner accepts the dependency. Files: `src/vended_plugins/skills/skill.rs`.

**P-385. URL skill sources are fetched on first use; the fetch has a crate-internal seam.** The TS constructor and `setAvailableSkills` start the fetches at once and every reader awaits `_ready`. A Rust constructor is synchronous and may run outside a runtime, so URL sources are kept pending and fetched (concurrently, under an async lock so every waiter sees them resolved) by the first of `init_agent`, the `BeforeInvocationEvent` hook, the `skills` tool or `get_available_skills`. Fetched skills are inserted in source order; TS inserts in completion order. `Skill::from_url` uses `reqwest` (user agent `strands-agents-sdk`, 30 second timeout); `Skill::from_url_with` and `AgentSkills::with_fetch` take a `SkillFetch` so tests answer without the network (TS spies on `globalThis.fetch`). The `resolved (including async)` debug line drops TS's `source_count` field.

**P-386. A failing skills hook logs and leaves the prompt.** TS `_setStateField` throws `TypeError: expected object for state key '<key>', got <type>` when the app state key holds a non-object; from the `BeforeInvocationEvent` hook that fails the invocation. Rust hooks return no error (as for the context manager, see the Phase 6 context-manager divergence), so the hook logs `error=<..> | failed to inject the skills into the system prompt` and the invocation proceeds with the prompt unchanged. From the `skills` tool the same error is the tool's error result, as in TS. A sandbox the agent cannot provide (`agent.sandbox()` failing) while path sources exist fails `init_agent`, and from the hook is logged the same way.
