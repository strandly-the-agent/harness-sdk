**P-1130. `shutdown_telemetry` is public: the caller's way to flush spans before exit (closes P-923).** Context: review finding correctness-8. With `OTEL_TRACES_EXPORTER=otlp` the SDK's `setup_tracer` wires a `BatchSpanProcessor`; the TS SDK flushes it on Node's `beforeExit` (`strands-ts/src/telemetry/config.ts:213-214`), and Rust has no exit hook, so a process that exits right after an invocation exported nothing. `create_harness` keeps the provider in a private static, so the caller had no handle to flush. Options: (a) export the existing `shutdown_telemetry`; (b) a `flush_telemetry` that calls `force_flush` and leaves the provider up; (c) return the provider or a guard from a new public setup function. Choice: (a), `pub async fn shutdown_telemetry() -> Result<()>`, re-exported from the crate root. The name is invented (PROMPT.md section 7.1; harness-ts exports no counterpart): it pairs with the TS `setupTelemetry` and mirrors what the SDK documents for its own setup, `shutdown()` on the provider `setup_tracer` returns, run off the runtime threads (`strands-rs/strands/src/telemetry/mod.rs`, `config/setup.rs`), and section 7.2's `shutdown().await`. (b) was not chosen because the SDK documents `shutdown()`, not `force_flush`, as the call before exit, and one name is the narrowest surface; (c) would add a second way to set telemetry up that TS lacks. The function exists with and without the `otel` feature (without it nothing is wired and it returns `Ok(())`), so a caller needs no `cfg`. It takes the provider out of the harness's slot: a second call does nothing, and agents that run afterwards export no spans (a later `create_harness` gets the SDK's already shut down provider back from `setup_tracer`). Documented on the function (with a doctest), in the crate-level docs and in `harness-rs/README.md`. The `create_harness` rustdoc (`agent.rs`, owned by track h12fa) gets a two-line pointer in a commit of its own. Test: `telemetry::tests::shutdown_telemetry_exports_the_spans_still_in_the_batch` (a batching provider over an in-memory exporter, scheduled delay of an hour, so only the flush exports). TS reference: `harness-ts/src/telemetry.ts`, `strands-ts/src/telemetry/config.ts:213-214`. Files: `harness-rs/strands-harness/src/telemetry.rs`, `src/telemetry/tests.rs`, `src/lib.rs`, `src/agent.rs` (rustdoc only), `harness-rs/README.md`.

**P-1131. The model call reads the tool registry after the `BeforeModelCallEvent` hooks (SDK change).** Context: review finding correctness-9. `ActiveRun::invoke_model` read `tool_specs` once, before the hooks, and passed that copy to the model; TS reads the registry again in `_invokeModelWithMiddleware` (`strands-ts/src/agent/agent.ts:2600`), after the hooks and on every attempt, so a tool a hook registers or removes (the MCP `tools/list_changed` refresh in `mcp/agent_tools.rs` among them) is in that call's request. Test: `agent::run::tests::hooks::a_registry_change_in_a_before_model_call_hook_reaches_that_calls_tool_specs`. Files: `strands-rs/strands/src/agent/run.rs`, `src/agent/run/tests.rs`.
