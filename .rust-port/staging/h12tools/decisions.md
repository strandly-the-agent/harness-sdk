**P-850. The harness file tools are functions that return a `FunctionTool`, with their own path check.** TS exports the tool objects `read`, `write` and `edit` from the package entry and keeps the factory `makeRead` internal (`tools/index.ts` exports it, `index.ts` does not); Rust has the public `read()`, `write()` and `edit()` and the `pub(crate)` `make_read(MakeReadOptions)` (`tools/file_tools.rs`, re-exported for the crate from `tools/mod.rs`), as the SDK's vended tools do. `MakeReadOptions.media` is `Option<bool>` (`None` is the TS default `true`). The harness keeps its own `validate_path` instead of the SDK's `vended_tools::paths::validate_absolute_path` (which is `pub(crate)`): `file-tools.ts:33-45` accepts what Node's `win32.isAbsolute` accepts, including a backslash-rooted path without a drive (`\foo`), which the SDK check rejects. `offset` and `limit` are JSON numbers (`z.number()`), so the window arithmetic is done in `f64` with JS `Array.prototype.slice` rules (a fractional or negative `limit` behaves as in TS).

**P-851. The harness `shell` module is one `pub(crate)` function over the SDK tool.** harness-ts has no shell of its own: `builtin-tools.ts:162` calls the SDK's `makeShell` with the `ShellConfig` (`description` only). `tools/shell.rs` has `pub(crate) fn make_shell(description: Option<String>) -> crate::Result<FunctionTool>`, which `builtin_tools` calls with `ShellConfig.description`; it is fallible because the SDK's `make_shell` is. The three cases of `shell.test.ts` run against it with a `NotASandboxLocalEnvironment` instead of a harness agent.

**P-852. `make_web_fetch` is infallible and its options have no `Default`.** `MakeWebFetchOptions { model: Arc<dyn Model>, transport: Option<WebFetchTransport> }` has a `bon` builder but no `Default`, because `model` is required in TS. The only TS failure of `makeWebFetch` is an unknown transport string, which the `WebFetchTransport` enum rules out, so the function returns a `FunctionTool`, not a `Result`. The tool owns its `ShellCache` (one probe per sandbox per tool; TS keeps one `WeakMap` for the module) and its URL cache, keyed by the URL as the model wrote it, with `tokio::time::Instant` expiry so tests use virtual time. The summarizer is a fresh `Agent` run with a plain `invoke`, as `web-fetch.ts:250-254` does: unlike the SDK's vended `web_fetch` analyst it gets neither the tool's cancel signal nor an auxiliary invocation context, so its usage is not added to the parent's.

**P-853. `web_fetch` is checked against the TS functions by golden output.** `tools/web_fetch/golden.json` holds the output of `curlCommand`, `powershellCurlCommand` and `htmlToText` from `harness-ts/src/tools/web-fetch.ts` at the pin, produced by evaluating those functions under Node; the tests compare the Rust commands and the HTML reduction byte for byte. Regenerate it when the TS functions change. `htmlToText`'s backreference pattern `<(script|style)…<\/\1>` is written as an alternation of the two tags, which matches the same text.

**P-854. The direct transport uses `reqwest` and caps the body while streaming.** `fetch_direct` reads `bytes_stream()` until 5 MiB have arrived and drops the response, as `readCapped` cancels the reader. The curl transport decodes the base64 body leniently, as Node's `Buffer.from(text, 'base64')` does (padding optional, characters outside the alphabet skipped). New dependencies of `strands-harness`, all already in `[workspace.dependencies]`: `reqwest`, `base64`, `regex`, `encoding_rs`.

**P-855. The Exa tool is behind the `mcp` feature; its backend takes an MCP seam and the env lookup.** `make_exa_web_search()` and `exa_web_search()` (public, re-exported) exist only with the `mcp` feature, because they are built over the SDK's `McpClient`; `builtin_tools` must gate its use the same way. `SearchResult`, `SearchBackend`, `WebSearchError`, `exa_backend` and `search_tool`, which `web-search.ts` exports but the package entry does not, are `pub(crate)` and compile without the feature. `exa_backend(api_key, env: EnvLookup, connector: ExaConnector)` reads `EXA_API_KEY` through the crate's env seam on every call, and gets its MCP client from `ExaConnector` (`Fn(ExaConnection) -> Result<Box<dyn ExaClient>, String>`), which the tests replace as the TS spec replaces `McpClient` with `vi.mock`. `exa_web_search()` builds a new tool on each call (TS has one module-level tool object); the tool has no state, so this is not observable.

**P-856. Two `dead_code` expectations of the skeleton were narrowed.** `sandbox.rs` lost its file-level `#![expect(dead_code)]` (web_fetch now uses every item). `env.rs` lost its file-level one: `process_env` and `EnvLookup` carry `cfg_attr(.., expect(dead_code))` for builds without the `mcp` feature, where only the gated Exa tool reads the environment. Drop those two attributes when another module uses the seam in every feature set.
