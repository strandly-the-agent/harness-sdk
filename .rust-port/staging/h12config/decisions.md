**P-930. `HarnessAgentOptions` shape (#32, #65).** An exhaustive struct with public fields, `Default` and a `bon` builder whose `build()` is infallible (nothing is validated until `create_harness`). The SDK passthrough is one field, `agent_config: strands::AgentConfig`, not flattened fields: TS `createHarness({ systemPrompt })` is `agent_config: AgentConfig { system_prompt, ..Default::default() }` in Rust. The six keys TS omits from the passthrough (`model`, `tools`, `plugins`, `interventions`, `background_tasks`, `context_manager`) are checked by `HarnessAgentOptions::check_passthrough()` (`pub(crate)`, for `create_harness` to call), which returns `HarnessError::PassthroughOption { key }` for the first one set; TS has no text for it (a type error there), so the text is Rust's: ``agent_config.<key> is a harness option: set `<key>` on HarnessAgentOptions instead``.

**P-931. One enum per polymorphic option.** `SessionOption`, `SkillsOption`, `MemoryOption` (`On` default, `Off`, `Config`/`Sources`, `Instance`), `CachingOption` (`Auto` default, `On`, `Off`: TS has an explicit `'auto'`), `BuiltinToolsOption` (`Names`, `Config`; the field is `Option`, `None` is the default set, which TS distinguishes from an explicit list), `McpServersOption` (`Path`, `Servers`). `session`, `skills` and `memory` have no `Auto`: TS treats unset and `true` alike. `false` and `null` are both `Off`. Fields that take an SDK union reuse the SDK's enum: `model: Option<ModelSource>`, `background_tasks: Option<BackgroundTasks>`, `context_manager: Option<ContextManagerOption>` where `ContextManagerOption` is an alias of `ContextManagerStrategy` (TS: "exactly the SDK's type plus `null`"; `Off` covers `false` and `null`). `effort: Effort` uses `Effort::Auto` as unset. Names are Rust's; TS has none for these unions.

**P-932. `Setting<C>` replaces TS `ToolConfig<K>`.** TS `boolean | ToolConfig<K>` is the generic `Setting<C> { On, Off, Config(C) }` (serde: a boolean or the config), also used for the portable `session` and `memory`. `ToolConfig` itself (a conditional type) has no Rust form. The `'*'` key of `BuiltinToolsConfig` and `HarnessConfigBuiltinTools` is the field `all`. `WebSearchSetting` is `On`/`Off`/`Exa` (serde: a boolean or `"exa"`).

**P-933. `McpServersOption::Servers` holds the JSON map.** `strands::mcp::McpServerConfig` exists only with the `mcp` feature, and the option type must not change with features, so the variant holds `JsonObject` (server name to the JSON form of `McpServerConfig`); with `mcp` on, `From<IndexMap<String, McpServerConfig>>` converts a typed map. `create_harness` parses it with the SDK loader.

**P-934. Portable config types.** `HarnessAgentConfig` is a typed struct (24 fields, serde camelCase) with `Default` equal to TS `DEFAULT_HARNESS_AGENT_CONFIG`, which is also the static of that name (a `LazyLock`, since the value owns strings). TS unions without a name got one: `HarnessConfigBuiltinToolsSetting` (`Names`/`Mapping`), `HarnessConfigMcpServers` (`Path`/`Servers`), `HarnessConfigSkills` (`Enabled`/`Source`/`Sources`), `HarnessConfigInterventions` (`One`/`Many`), `HarnessConfigModel` (`Id`/`Module`). `HarnessConfigContextManager::Off` serializes as `false`. `ProgrammaticToolCallerConfig` fields are `Option<Option<T>>` (absent, `null`, value) because TS keeps `null` distinct from absent (`timeout: null` is no bound, absent is 900). `HarnessModuleReference` keeps unknown keys in `extra` (TS `looseObject`). `Deserialize` for `HarnessAgentConfig` runs the normalization, so a config read from JSON is validated; the nested types derive `Deserialize` without it.

**P-935. Normalization.** `define_harness_agent_config(&JsonValue)` is the public entry (TS `defineHarnessAgentConfig`: defaults merged, then normalized; with JSON input the two steps are one). `normalize_harness_agent_config` is `pub(crate)`: TS does not export it from the package entry. The validator is hand-written to produce the TS issue lines (zod schemas plus `formatIssues`): issues in schema order, a `strictObject`'s unknown-keys line after its field lines, a failed union reported through its one type-matching branch. `must contain only JSON-compatible values.` cannot occur (a `serde_json` value is JSON). Errors: `HarnessError::ConfigNotObject`, `HarnessError::InvalidConfig { issues }`.

**P-936. `harness_agent_options_from_config(config, base_dir: Option<&Path>)`.** Synchronous (TS is async only to load modules); `None` is the current directory, as TS `process.cwd()`. The crate-internal seam is `config::options::options_from_config(config, base_dir, env: &EnvLookup)`. `~` expands from `HOME`, then `USERPROFILE`, read through the env seam (TS `os.homedir()`); neither set is `HarnessError::EnvVarNotSet { name: "HOME" }`. Paths are joined to `base_dir` and folded lexically like Node's `path.resolve`; a relative `base_dir` stays relative. The MCP config file is read from the host with `std::fs` (as TS `readFileSync`; no agent or sandbox exists yet).

**P-937. Module references.** Any reference (`tools`, `subagents`, `plugins`, `sandbox`, `memoryStores`, `modelModule`, `builtinTools.web_fetch.model`, `interventionModules`, `agentConfigModules`; first in that order) makes the bridge return `HarnessError::ModuleReferenceUnsupported { language }`, text per PROMPT.md section 10. Normalization still accepts and keeps references, so a config with them can be read, inspected and written back.

**P-938. `agentConfig` keys the bridge applies.** TS spreads `agentConfig` into the options untyped. Rust applies `name`, `description`, `id`, `systemPrompt`, `messages`, `appState`, `modelState`, `printer`, `auxModel`, `baggageAttributes` (to `agent_config`) and `backgroundTasks` as a boolean (to `background_tasks`); a value of the wrong type is `HarnessError::InvalidAgentConfigValue { key, message }`; any other key is dropped with one warning, `Ignoring agentConfig keys that are not supported in Rust: <sorted keys>.`. Pending for the owner: whether an unsupported key should be an error instead.

**P-939. Placeholder for `InterventionsOption`.** `interventions.rs` has a minimal `InterventionValue { Text(String), Handler(Arc<dyn InterventionHandler>) }` and `InterventionsOption { One, Many }` in the commit `chore(harness): placeholder for InterventionsOption`, plus their `pub use` line in `lib.rs`. `config/options.rs` builds them in `interventions(..)` and `config/tests.rs` matches on them in `intervention_texts(..)`; adapt those two places if the real type differs.

**P-940. `HarnessError` variants added.** `ConfigNotObject`, `InvalidConfig { issues }`, `ModuleReferenceUnsupported { language }`, `McpConfigInvalidJson { path, source }`, `McpConfigNotServerMap { path }`, `McpServersNotServerMap`, `EnvVarNotSet { name }`, `InvalidAgentConfigValue { key, message }`, `PassthroughOption { key }`, and the helper `error::json_quote` (`pub(crate)`, TS `JSON.stringify` of a string).

**P-941. Skeleton `expect`s removed.** `env.rs` and `logging.rs` lost their file-level `#![expect(dead_code)]`: the config module uses every item of both, so the expectation was unfulfilled.
