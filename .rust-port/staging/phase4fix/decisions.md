**P-97. A sub-agent joins only the abort of its parent's signal.** TS `agentAsTool` and the vended `subagent` tool pass the parent's `AbortSignal` to the child (`agent.ts:1273-1274`); a deferred cancel (`after_current_tools`) only sets the parent's private `_deferredCancel`, and the child's after-batch check reads its own (`agent.ts:1996`). Rust passed the parent's `CancelSignal` itself, whose `is_deferred()` and `reason()` fall back to the joined signal, so a parent's deferral stopped the child after its first batch (with the cancel text as a successful answer) and an immediate parent cancel with a message became the child's final message. Choice: `CancelSignal::abort_only()` (crate-internal) builds a signal on a child token with no joined parent; `as_tool` and `subagent` forward it. The child is still aborted when the parent is, ends with `Cancelled by user`, and runs to completion under a parent's deferred cancel. `InvokeOptions::cancel_signal` from user code keeps its message and deferral (DIVERGENCES).

**P-98. Drops during initialization and during the deferred hooks; P-98 amends P-91.** A dropped `invoke`/`initialize` future can stop at any `await`, which a TS promise can't. Choices: (1) `PluginRegistry` keeps a cursor of finished plugins and records a plugin's name only after its `init_agent` returns, so the next call resumes at the plugin that was awaiting instead of skipping the rest (a plugin dropped mid-`init_agent` runs it again from the start). (2) `AbandonedRun` stays on the agent until its hooks return: the `MessageAddedEvent` repair is cleared once its hooks return, the run once `AfterInvocationEvent` returns (an `Err` from either also clears it), so a call dropped while they run leaves them for the next `invoke`, `stream` or `shutdown`, and the drop warning still fires. (3) The deferred hooks run under a fresh, cancelled signal that the agent's cancel handle targets (P-91 treats a drop as a cancel), so the background-task `AfterInvocationEvent` hook skips its wait as TS does when `cancelSignal.aborted`; the signal is reset after the hooks.

**P-99. An empty hook cancel message is no cancel.** TS tests `cancel` for truthiness (`agent.ts:1294, 2441, 2797`, `tools/executors/executor.ts:145`), so `event.cancel = ''` doesn't cancel. Choice: `Cancel::Message("")` is treated as no cancel where the loop and executor read it (`BeforeInvocationEvent`, `BeforeModelCallEvent`, `BeforeToolsEvent`, `BeforeToolCallEvent`); the `cancel()` getters still return what the hook set.

**P-100. `Agent::cancel_signal` is removed; P-100 amends P-90's name list.** `Agent::cancel_signal()` borrows the agent, which a running `stream`/`invoke` holds mutably, so it could only ever return the fresh idle signal. The running invocation's signal is read where TS code reads `agent.cancelSignal`: `LocalAgent::cancel_signal` (hooks), `ToolAgent::cancel_signal` and `ToolContext::cancel_signal` (tools). Cancelling from outside goes through `Agent::cancel_handle()`.

**P-101. `BackgroundTasks` names the config-key union; P-101 adds to the P-15 name map.** TS `BackgroundTasks` is the plugin class (`background-tasks/background-tasks.ts:49`), and the `backgroundTasks` config key's type `boolean | BackgroundTasksConfig` has no name. The Rust plugin is crate-internal (`BackgroundTaskScheduler`) and never named by users, while the config key needs a public type. Choice: keep `strands::background_tasks::BackgroundTasks` for the public union (`Disabled`, `Enabled`, `Config(BackgroundTasksConfig)` with `From<bool>` and `From<BackgroundTasksConfig>`), read at the same place a TS user writes `backgroundTasks: ...`; the TS class name points at the config-key concept in Rust, and the plugin keeps the invented internal name.

**P-102. Conversation-manager configs are plain config structs; P-102 amends P-96.** `SlidingWindowConversationManagerConfig` and `SummarizingConversationManagerConfig` drop `#[non_exhaustive]` for `#[expect(clippy::exhaustive_structs, reason = "config struct: struct-literal construction")]` (#65), so `..Default::default()` works from other crates, and the sliding-window config derives `Clone` only (adding a non-`Copy` field later won't break callers). The token-usage `percent` formats the `f64` `used / limit * 100` with one decimal and rounds exact ties up (an exact tie is an odd multiple of 0.25 in the `f64`), which matches TS `toFixed(1)` on the binary value (P-96 said half-up on the exact fraction, which differs, e.g. 300/200000 is `0.1` in TS).
