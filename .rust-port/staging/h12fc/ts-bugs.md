# TS bugs, track h12fc (entries for `.rust-port/ts-bugs.md`)

**A second agent on one `McpClient` stops the first from refreshing its MCP tools.** `strands-ts/src/agent/agent.ts:885` assigns `client.onToolsChanged` in `Agent.initialize`, and the client has one slot (`strands-ts/src/mcp/client.ts:394,751-753`). The last agent to initialize on a client is the only one whose registry follows `notifications/tools/list_changed`; once that agent is garbage, nobody does. The harness builds every delegate on the parent's client instances (`harness-ts/src/builtin-tools.ts:193-215`, `mcpClientsByClientName`, the `mcp_servers` axis), so after the first delegation the parent keeps its stale MCP tool list. Repro: `.rust-port/reviews/phase12-review-correctness-probe/ts-diff/mcp.ts` (a stdio server whose `mutate` tool adds a tool and sends the notification): without a delegation the parent's later request lists the new tool, after one delegation it never does. Rust keeps one change queue per agent on the client (P-1140).

**A background task that interrupts after the model ended its turn makes the resumed invocation call the model with nothing new.** `strands-ts/src/background-tasks/background-tasks.ts:275-277` (`_afterInvocation`) sets `event.resume ??= []` when a task needs input, and `_beforeModelCall` (`:236-259`) raises the interrupt on that pass. When the caller answers, `_beforeModelCall` resumes the task and returns with nothing to deliver, so the model is called with a history that ends in its own assistant message; its reply is appended as a second assistant message in a row, and the task's result is merged into that one later. Repro: `.rust-port/reviews/phase12-review-correctness-probe/ts-diff/intr.ts` (default harness, `interventions: "ask"`, the parent delegates and ends its turn, the child asks to approve `shell`): request roles `user | assistant | user | assistant`, then `... | assistant | assistant | user`. Providers that require alternating roles or a final user message can reject both requests (not checked against a live provider). Rust waits for the resumed task and delivers its result before the next model call when `waitForCompletion` is on; with `waitForCompletion: false` Rust still does what TS does (P-1141).
