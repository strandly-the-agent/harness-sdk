# Decisions, track h12fc (entries for `.rust-port/DECISIONS-pending.md`)

**P-1140. Tools-list changes fan out to every agent on an `McpClient`.** Review finding correctness-6. `mcp::agent_tools::initialize` no longer calls `McpClient::set_on_tools_changed`; it registers the agent's change queue with the crate-private `McpClient::queue_tools_changed`, which keeps a `Weak` to it (the queue is owned by the agent's `BeforeModelCallEvent` hook, so it dies with the agent; dead entries are pruned on every registration and every refresh). `refresh_tools` pushes the change to every live queue and then calls the `set_on_tools_changed` callback. No public API change. Consequence that differs from TS: a callback the consumer set with `set_on_tools_changed` is no longer replaced when an agent initializes on the client. PENDING: confirm that keeping the consumer callback is wanted (the alternative, clearing it on agent initialize as TS does, has no use the port could find). Files: `strands-rs/strands/src/mcp/client.rs`, `strands-rs/strands/src/mcp/agent_tools.rs`, `strands-rs/strands/src/mcp/tests.rs`.

**P-1141. A background task resumed after the turn ended is waited for before the next model call; `wait_for_completion: false` is undecided.** Review finding correctness-5. `BackgroundTaskScheduler::before_model_call` is now an async hook: when the invocation's interrupt responses resumed at least one task and the last message of the history is an assistant message, it runs the same wait as `after_invocation` (until no task runs, a task asks for input, or the invocation is cancelled) and then raises the new interrupts or delivers the finished tasks. The delivered messages and the persisted task and message formats are unchanged. The existing TS case `surfaces_and_resumes_interrupts_from_detached_tools` still passes. Not changed: with `wait_for_completion: false` the hook may not wait, so the resumed invocation still calls the model with a history ending in an assistant message, as TS does. PENDING, options for that case: (a) the agent loop skips the model call of a pass that added no message and ends the invocation with the previous result (a change in `agent/run.rs`, for both SDKs); (b) the scheduler raises nothing and returns the interrupt only on the caller's next invocation (changes when the caller sees the interrupt); (c) keep it and document that `wait_for_completion: false` with interrupting background tools needs a provider that accepts a trailing assistant message. Files: `strands-rs/strands/src/background_tasks/background_tasks.rs`, `strands-rs/strands/src/background_tasks/background_tasks/tests.rs`.

**P-1142. Built-in plugins are recognised by what they contribute, not by a downcast (extends P-958).** Review finding correctness-3. P-958 proposed an `as_any` on the SDK `Plugin` trait; decision #15 excludes `Any`, `TypeId` and downcasting from the public API, so the harness uses signals the trait already gives. `select_builtin_plugins` skips a built-in when a consumer plugin has the same `name()` or, for a built-in that vends tools, returns the same tool specs from `Plugin::get_tools` (this is what recognises a `Todos` built with a custom name; it runs before the tool-name collision check, which a `Todos` under a custom name used to fail). `EnvironmentContext` vends no tool and exposes nothing else before `init_agent`, so the harness adds its own instance through the crate-private `EnvironmentContext::yielding`: at injection time it returns nothing when the latest message of the model call already holds an injected block that starts with `<system-reminder>\n<environment>\n` (consumer plugins initialize first, so their injector runs first). Two consumer instances still inject one block each, as in TS. `has_skills` is unchanged: `AgentSkills::name()` is the constant `AgentSkills::NAME`, so recognition by name is exact there. Differences from TS that remain: the built-in `EnvironmentContext` is registered (and idle) next to a consumer one with a custom name; a plugin that is not a `Todos` but vends an identical `todo_write` spec, or is not an `EnvironmentContext` but injects a block with the same opening, is taken for one. PENDING: accept these, or add a typed marker to the SDK `Plugin` trait that is not a downcast (for example a `kind()` string defaulting to `name()`), which would be an SDK API addition. Files: `harness-rs/strands-harness/src/agent.rs` (`select_builtin_plugins` only), `harness-rs/strands-harness/src/plugins/environment.rs`, `harness-rs/strands-harness/src/plugins/environment/tests.rs`, `harness-rs/strands-harness/src/plugins/todos/tests.rs`.
