# Dispositions, track h12fc (Phase 12 correctness review)

| finding | disposition | commit |
|---|---|---|
| correctness-6 | Fixed in the SDK. An agent that lists an `McpClient`'s tools adds its own change queue to the client (`McpClient::queue_tools_changed`, crate-private, held weakly, pruned once the agent is dropped) instead of replacing the single `set_on_tools_changed` callback, so a delegate built on the parent's client no longer stops the parent's refresh. `set_on_tools_changed` stays the consumer's callback and is called as well. Tests in `strands-rs/strands/src/mcp/tests.rs` (`tools_list_changed`): `an_agent_still_replaces_its_mcp_tools_after_another_agent_used_the_same_client`, `every_agent_on_a_client_and_its_on_tools_changed_callback_see_a_list_change`, `a_dropped_agent_is_no_longer_queued_for_tools_list_changes`. TS bug and divergence row staged; P-1140. | 72e1f3af4 |
| correctness-5 | Fixed in the SDK for the default `wait_for_completion: true` (the harness path). When the caller's answers resume a background task and the history ends in an assistant message, `BackgroundTaskScheduler::before_model_call` waits for the task as `after_invocation` does and delivers its result, so the next request ends in the delivered tool result and no model call is made with nothing new. Message and task formats are unchanged (the delivery is the same synthetic `get` pair, merged into the last assistant message as before). With `wait_for_completion: false` nothing may wait, so the sequence stays as in TS; that part needs a loop-level decision (P-1141). Test: `strands-rs/strands/src/background_tasks/background_tasks/tests.rs::a_task_resumed_after_the_turn_ended_is_delivered_before_the_next_model_call`. TS bug and divergence row staged. | c7eb0bd60 |
