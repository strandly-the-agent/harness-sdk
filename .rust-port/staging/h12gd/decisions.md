**P-1195. Typed tool input: undeclared keys are dropped before validation (zod `strip`).** Review finding parity-13. `InputValidator::parse` (the one validator behind `FunctionTool::typed`, `#[tool]`, the vended tools and the harness tools) clones the input, removes the keys an object schema with `additionalProperties: false` does not declare, using the `strip_unknown_properties` walk structured output already had (now `pub(crate)`; it follows `properties` and `items`), validates the stripped value with `jsonschema` and deserializes it. The published schemas keep `additionalProperties: false`, as `z.toJSONSchema` prints for a plain `z.object`. zod's strict form has the same published schema, so the schema cannot tell the two apart; the Rust strict form is the input type: when keys were dropped and the type does not deserialize from the original input though it does from the stripped one (`#[serde(deny_unknown_fields)]`), the call fails with the `jsonschema` error of the original input, the text it had before this change. Schemas that allow additional properties (`true`, a schema, or absent on a hand-written schema) are not stripped. `InputValidator` gained a private `schema` field; no public signature changed. Not reached by the strip, and still a validation error: an undeclared key inside an `anyOf`/`oneOf` branch, inside a record value (`additionalProperties: <schema>`), or inside a recursive type kept as `$ref` (SDK DIVERGENCES row staged). Alternative considered: stripping in each harness tool before `validator.parse`; rejected because `#[tool]` functions and SDK vended tools reject the same calls.
