**P-1120. `agentConfig` keys the bridge applies (replaces P-938).** TS spreads `agentConfig` into the options before the top-level keys (`harness-ts/src/config.ts:370-393`) and the rest into `new Agent` (`agent.ts:364,512`). Rust applies, typed: `name`, `description`, `id`, `systemPrompt`, `messages`, `appState`, `modelState`, `printer`, `auxModel`, `baggageAttributes`, `traceAttributes` (string, number, boolean, or a homogeneous array of one), `toolExecutor` (`"concurrent"` or `"sequential"`), `sandbox: false`, `retryStrategy: null` or `[]`, `backgroundTasks` (boolean or `{ waitForCompletion, agentic, always, never, maxConcurrency, timeout }` with tool names and `timeout` in milliseconds; an unknown key in the object is an error), and the harness keys `instructions`, `caching` (`"auto"`, boolean, `null` as `false`), `builtinTools`, `builtinPlugins`, `mcpServers` (a path or a map, passed on as written: no `cwd`, no placeholder expansion, as in TS), `interventions` (texts as written: no `.cedar` path resolution, as in TS). The last four and `instructions`, `caching`, `description` take effect only when the top-level key is at its default, as in TS. `model`, `effort`, `contextManager`, `session`, `skills`, `memory` under `agentConfig` are skipped without a warning: the top-level config always sets them, so TS never reads them there either. `builtinTools`, `builtinPlugins` and `interventions` under `agentConfig` are held to the rules of the top-level keys, reported as `Invalid agent config:` with the path under `agentConfig.`. Keys whose TS values are live objects, or that have no Rust field (`tools`, `plugins`, `conversationManager`, `structuredOutputSchema`, `sessionManager`, `memoryManager`, `checkpointing`, `storage`), are `HarnessError::UnsupportedAgentConfigKeys { keys }` (`agentConfig keys are not supported in Rust: <sorted keys>.`); a `sandbox` or `retryStrategy` value without a JSON form is `InvalidAgentConfigValue`. A key that is in neither SDK's options is dropped with one warning, `Ignoring unknown agentConfig keys: <sorted keys>.`, the treatment TS gives an unknown top-level key. This answers the question P-938 left open with "error" for every key TS would act on. Pending for the owner: whether a key neither SDK reads should be an error too, and whether the six always-overridden keys should warn.

**P-1121. `subagent.maxDepth` above `u32::MAX` saturates.** TS accepts any non-negative safe integer (zod `int()`, checked at the pin: 9007199254740991 passes, 9007199254740992 fails). Rust accepts the same range and holds a value above `u32::MAX` as `u32::MAX`, so the config serializes back with the clamped value. The depth guard only counts down, so the two are indistinguishable at run time.

**P-1122. What the harness `Debug` impls redact.** `redact_mcp_servers` replaces, per server entry, every value under `env` and `headers` (the whole value when it is not an object) and every key of `auth` except `clientId` and `scopes`; it handles the flat map and the map under `mcpServers`. Used by `HarnessConfigMcpServers`, `McpServersOption` and `HarnessAgentConfig` (for `agentConfig.mcpServers` too). `HarnessAgentConfigBuilder` has an opaque `Debug` (`HarnessAgentConfigBuilder { .. }`) instead of bon's derived one, which would print `agent_config` raw. Not redacted: `url` and `args`, which the SDK's typed config prints as well.
