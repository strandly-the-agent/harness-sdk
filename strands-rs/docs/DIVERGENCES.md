# Divergences from the TypeScript SDK

This file lists every user-visible behaviour difference between the Rust SDK (`strands`) and the TypeScript SDK, with the reason for it. The TypeScript SDK (`strands-ts/`) is the specification, so a difference is recorded here only when Rust can't or shouldn't match it, for example where the language rules out the TypeScript mechanism. Differences in API shape that follow Rust idiom (builders, `Result`, `snake_case` names) aren't listed. A fix never changes a cross-SDK wire or persisted format: data written by either SDK keeps loading in the other.

| Area | TypeScript | Rust | Reason |
|---|---|---|---|
| JSON strings | A string can hold a lone UTF-16 surrogate, written as `\ud83d` | A lone surrogate escape fails to parse; load paths replace it with U+FFFD before parsing | Rust strings are valid UTF-8 and can't hold a lone surrogate |
| JSON nesting | No nesting limit beyond the call stack | Parsing stops at 128 nested arrays or objects | `serde_json`'s recursion limit guards against stack overflow |
| Counters | `Usage`, `Metrics` and citation positions are `number` | `u64`; a fractional `Usage` or `Metrics` value fails to load, and a citation location with a fractional position loads as `CitationLocation::Other`, written back unchanged | Integer types keep integers free of a `.0` suffix; TS never writes fractions there |
| Citations | `CitationsBlock` keeps the saved citation objects as read, so `JSON.stringify` writes back any key order, field type and block shape; a `content` item whose `text` is `null` makes the token estimate throw a `TypeError` | A citation and its `sourceContent` and `content` items keep their key order, unknown keys, and `null` or missing fields, and a location that doesn't fit its `type` loads as `CitationLocation::Other`, all written back as read. But a location that fits a known `type` is written with `type` first and its fields in the order the variant declares them (`{"url":"u","type":"web"}` is saved as `{"type":"web","url":"u"}`); a field of the wrong type (`"title": 5`, a string `location`, a `null` item in `sourceContent`) or a block whose `citations` or `content` isn't an array fails to load; and a `null` `text` counts as 0 tokens | Rust reads citations into typed fields. Every TS provider builds locations with `type` first in the declared order, and none writes the other shapes |
| Large JSON integers | An integer above 2^53 in loaded JSON is rounded to the nearest double (`9007199254740993` is saved back as `9007199254740992`) | Integers up to the 64-bit range keep every digit when loaded and saved | Rust parses JSON integers into `u64`/`i64`; data TS wrote never holds such an integer, so TS-written bytes round-trip unchanged |
| Unknown blocks | `new UnknownBlock(data)` accepts any object, so one built from `{"text":..}` loads back as a `TextBlock` | `UnknownBlock::new` returns `None` when the data holds a known content-block or tool-result-content key | A block that changes type on a round trip is a bug, not behaviour to keep |
| MIME lookup | `toMimeType('constructor')` returns an object-prototype function | Returns `None` | TS looks up a plain object literal, so prototype keys match |
| Concurrent invocation | A second `invoke` while one runs throws `ConcurrentInvocationError` | No such error; `invoke` borrows the agent mutably, so a concurrent call doesn't compile | The borrow checker rules the case out; callers who share an agent wrap it in `Arc<Mutex<Agent>>` |
| Tool result errors | `ToolResultBlock.error` holds the thrown value, checked with `instanceof` | `error()` returns `&(dyn std::error::Error + Send + Sync)`; finding the concrete type takes a downcast | A tool can fail with any error type, not only `strands::Error` |
| Structured output support | Mechanisms a model rejected are remembered process-wide, keyed by provider and model id | Remembered per provider instance; a new instance learns a rejection again on its first failing request | The SDK keeps no process-global mutable state other than warn-once sets |
| Rejected native output schemas | Remembered per Zod schema object | Remembered per schema JSON text, so equal schemas share the record | Rust schemas are JSON values without object identity |
| `StateStore.set` errors | Path-specific `JsonValidationError` texts for functions, symbols and `undefined` | `JsonValidationError` `value for key "<key>" cannot be serialized: <reason>`, for values whose `Serialize` fails | Rust values can't hold functions, symbols or `undefined`; serialization fails for other reasons |
| Summarize warning | Names the model class (`model=<BedrockModel>`) | Names the model id (`model=<global.anthropic.claude-sonnet-4-6>`) | A `dyn Model` has no class name |
| Tool input validation errors | A Zod tool's invalid input gives `Error: <ZodError message>`, a JSON list of issues | `Error: <path>: <message>`, one line per `jsonschema` violation (no path at the root), with a `ToolValidationError` as the result's error | Zod's issue format is specific to Zod; the result is still an error-status tool result |
| Typed tool input | Zod `.parse` strips unknown keys and rejects `null` for `.optional()` fields | Validation follows serde: unknown keys pass and `null` reads as `None` for an `Option` field, although the advertised schema closes objects and omits `null` | The input is deserialized with serde, so validation accepts what deserialization accepts |
| Tool input schemas | `z.toJSONSchema` adds safe-integer bounds to `int`, lists defaulted fields as required with `default` first, adds `propertyNames` to records, and adds regex `pattern`s to `email`, `uuid` and `datetime` | Integers carry only their type's bounds, defaulted fields are optional with `default` after the type, maps have no `propertyNames`, and formats come without patterns | The schema is derived from Rust types through `schemars`; the shape otherwise matches Zod (see `tools/schema.rs`) |
| Tool descriptions | `tool({ .. })` without `description` creates a tool with description `''`, which the registry then rejects | `#[tool]` without a doc comment is a compile error | Reports at compile time the failure TS reports when the agent is built |
| Streaming tool callbacks | `FunctionTool` and `tool()` callbacks may be async generators whose yields become `ToolStreamEvent`s | `FunctionTool` callbacks are async functions; a streaming tool implements `Tool` and returns a `ToolStream` | Rust has no stable generators |
| Structured output on a result | `result.structuredOutput` is `undefined` when the invocation produced none | `result.structured_output::<T>()` returns a `StructuredOutputError` (`the result has no structured output`) when there is none, and an error when the value doesn't deserialize as `T` | Typed access returns `Result` instead of an untyped optional field |
| Result text of skipped blocks | `AgentResult.toString()` logs `Skipping content block type: <type>` at debug level for each non-text block | Non-text blocks are skipped without a log line | `Display` stays free of side effects |
| Hook failures | A hook callback that throws fails the invocation, and later callbacks of the event don't run | Hook callbacks return nothing and can't fail; a hook stops work by setting `cancel` | Typed, infallible callbacks (`Fn(&mut Event)`); errors as control flow would need a fallible signature on every hook |
| Hook interrupts | `event.interrupt(..)` throws, ending the callback | `event.interrupt(..)` returns `Err(Interrupt)` and records it; the callback returns on its own, and an interrupt it ignores is still collected | Interrupts are never modelled as errors or panics |
| Hook control fields | `cancel` is `boolean \| string`, `endTurn` is `boolean \| string \| ContentBlock[]` | `Option<Cancel>` (with an optional message) and `Option<EndTurn>` (`DefaultMessage`, `Message`, `Content`) | Typed values instead of unions |
| Agent without a model | Creates the default `BedrockModel` | Until the Bedrock provider is in the build, the first model call fails with `DefaultNotConfiguredError` | The default model resolves lazily so building an agent stays synchronous |
