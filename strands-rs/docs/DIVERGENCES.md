# Divergences from TypeScript

Every user-visible behaviour difference from the TypeScript SDK, with the reason. A divergence never changes a cross-SDK wire or persisted format.

| Area | TS behaviour | Rust behaviour | Reason |
|---|---|---|---|
| Message tracking ids | `crypto.randomUUID()` (UUID v4) | UUID v7 | Time-ordered ids from the `uuid` crate; any non-empty string is still accepted |
| Lone UTF-16 surrogates in saved JSON (`"\ud83d"`) | Kept in the string | The SDK's readers replace each with U+FFFD; `serde_json::from_str` rejects them | Rust strings are UTF-8 and can't hold lone surrogates |
| `Uint8Array` fields saved as `JSON.stringify` index objects (`{"0":1}`) | Re-encoded as the base64 of `"[object Object]"` | Read as the original bytes, written as base64 | The TS behaviour corrupts the bytes (see the TS bug list) |
| Serializing a single block struct (`AudioBlock`, `ToolUseBlock`, ...) | `block.toJSON()` returns the wrapped form `{"audio": ..}` | The struct serializes its inner object; `ContentBlock` adds the wrapper | Wire JSON of messages and content blocks is identical; only standalone block serialization differs |
| Pending interrupt message saved without `trackingId` | Raw data kept as saved | Parsed as a `Message`, so a tracking id is minted and written back | Interrupt state is typed |
| Fractional `latencyMs`/`timeToFirstByteMs` | Kept as a fraction | Rounded to whole milliseconds on load | Counters are integers so they never gain `.0` |
| `latencyMs: null` in saved metrics | Kept as `null` | Loads as `0` | `latency_ms` is a required integer; the message still loads (a `null` `timeToFirstByteMs` loads as missing, as in TS) |
| Strict parsing of a malformed known block | Throws whatever the block constructor throws (often a `TypeError`) | `Error::Other` with the serde message | Only the unknown-block texts are part of the contract |
| `SandboxTimeoutError` constructor | Takes seconds as a number | Takes a `Duration`; the message text is the same | Rust-native durations |
| `StateStore.set` with a value JSON can't hold | Throws `JsonValidationError` naming the path of the function, symbol or `undefined` | Returns `JsonValidationError` with `value for key "<key>" cannot be serialized: <reason>` | Rust values can only fail inside their `Serialize` impl, which has no path |
| Constructing an `UnknownBlock` | `new UnknownBlock(data)` accepts any record, including a known block's data (which reloads as that block) | No public constructor; an `UnknownBlock` comes only from deserializing data no known block matches | Keeps the block type stable across a save and load (see the TS bug list) |
| A hook callback that fails | A thrown error aborts the remaining callbacks and propagates out of the invocation | Callbacks return `()` and can't fail; a hook stops work through the event's control fields (`set_cancel`, `interrupt`) | Errors aren't control flow; hooks that need to fail an invocation cancel it with a message |
| Raising an interrupt from a hook | `event.interrupt(..)` throws, ending the callback | `event.interrupt(..)` returns `None` (or the stored response on resume) and records the interrupt; the callback keeps running and decides what to do next | No exceptions in Rust; collection and the duplicate-name error text are unchanged |
| Typed tool input that fails validation | Zod's error text (`Error: [{..issues..}]`) | `Error: Invalid input at /path: <jsonschema message>` or `Error: Invalid input: <serde message>` | Zod messages can't be reproduced; the result is still an error result the model sees |
| A defaulted field of a typed tool | Zod output-mode schemas list it in `required` | Optional in the schema (schemars); the default applies when absent | Validation runs before deserialization, so a required-in-schema field would reject input Zod accepts |
| JSON nesting depth on read (saved data, model tool input) | `JSON.parse` loads any depth | More than 500 levels of arrays/objects is a parse error; model tool input that deep is the `unable to parse tool input JSON` model error | Cloning and dropping deeper values can overflow a thread stack and abort the process |
| A content block after tool input that fails to parse | Becomes a tool use with the failed block's id and name (see the TS bug list) | Is its own block (the text is kept) | TS bugs are fixed in Rust (#74) |
| Structured output mechanisms a model rejected | Remembered process-wide for every provider | Remembered per provider instance; a new instance can repeat one failed request per mechanism | No process-global mutable state |
| `updateConfig`/`merge` with a field set to `undefined`/`None` | The spread unsets the field | `None` keeps the current value; replace the config to clear a field | `Option` can't tell "unset" from "absent" |
| A tool that panics | No equivalent; a throwing tool body becomes an error result with the error message | An error result whose text is the panic message; `AfterToolCallEvent` fires as for a failure | Rust panics are caught per tool so siblings and the invocation continue |
| Two tools of a concurrent batch interrupt | `InterruptEvent` fires for the last interrupted tool only (see the TS bug list) | The batch reports every interrupt | TS bugs are fixed in Rust (#74) |
| Changing an event from the stream consumer | The consumer gets the live event and can set `cancel`, `retry`, ... before pulling the next one | The stream yields owned, read-only records; changes go through hooks | `Agent` takes `&mut self`, so the stream can't hand out the live events that borrow it (section 8.6) |
| No model configured, without the `bedrock` feature | `new BedrockModel()` in the constructor | A placeholder whose first model call fails with `DefaultNotConfiguredError` (with `bedrock`, the default is `BedrockModel` as in TS) | The Bedrock provider is an optional cargo feature |
| Concurrent invocations of one agent | `ConcurrentInvocationError` at runtime | A compile error: `invoke`/`stream` take `&mut self`; share through `Arc<tokio::sync::Mutex<Agent>>` | Decision #22 |
| Stream result | The generator's return value; `AgentResultEvent` yielded separately | The last stream item is `AgentStreamEvent::AgentResult`; `invoke` drains the stream and returns it | A `Stream` has no return value |
| Interleaving of a concurrent batch's events across tools | Fixed by the microtask order of one `Promise.race` loop | Each tool's own event order matches TS; how events of different tools interleave depends on task scheduling | Each tool runs on its own task (section 8.8) |
| A `BeforeInvocationEvent` cancel | The denial message skips `MessageAddedEvent` hooks and no `AgentResultEvent` fires | Both fire | TS bugs are fixed in Rust (#74) |
| Local tool traces of concurrent tools | The last-started tool's trace is ended by whichever tool finishes first | Each tool's trace ends when that tool finishes | TS bugs are fixed in Rust (#74) |
| `InvokeLimits` values | Positive finite numbers, fractions allowed; zero, negative, non-finite and unknown keys throw `TypeError` at invoke | `NonZeroU32`/`NonZeroU64` fields of a struct, so those errors are compile errors; a fractional TS limit `n.5` behaves as `n + 1` | Counters are integers, so `>= 2.5` and `>= 3` stop at the same count |
| A foreign `InvocationContext` | `invocationContext was not created by the SDK` (`TypeError`) | Can't be built outside the SDK (no public constructor) | Type system |
| Structured output validation messages | zod's error message (a JSON list of issues) | `Invalid input at <path>: <message>` per violation, joined with `; `, from `jsonschema`; zod's strip of undeclared keys and its `format` checks are reproduced | No zod in Rust; the schema comes from `schemars` |
| A retry strategy attached to two agents | Throws while the first agent object exists, forever | Throws while the first agent is alive; dropping it releases the strategy | Attachment is tracked through weak handles |
| Direct tool call ids | `tooluse_` + `crypto.randomUUID()` (v4) | `tooluse_` + UUID v7 | Same id source as tracking ids |
| A direct tool call whose tool throws or panics | A raw `Tool` that throws rejects `invoke`; `context.interrupt` throws `Interrupts are not supported in direct tool calls` | A panicking tool fails the call with `Err` carrying the panic message; a tool that raises an interrupt gets the error result `Error: Interrupts are not supported in direct tool calls` (what a TS function tool returns), and the interrupt never reaches the agent | Rust tools can't throw; failures are results (#39) |
| `agent.asTool()` and agents in `tools` | The tool references the agent, which the caller keeps using | `Agent::as_tool(self, ..)` (and `From<Agent> for ToolSource`) moves the agent into the tool; `AgentAsTool::with_agent` reaches it between calls | `Agent` methods take `&mut self`; the tool owns the agent and lends it to one call at a time |
| Delegate agent events in the parent stream | The parent re-dispatches each surfaced child event to its own hooks (`event.agent` tells them apart) and skips its `ToolStreamUpdateEvent` hooks for them | The parent yields the child's records without dispatching them to its hooks; its `ToolStreamUpdateEvent` hooks are skipped too | Records aren't hook events; the parent's hooks already saw their own events (see the TS bug list) |
| `load_snapshot` with a field that doesn't parse | Restores field by field and throws at the bad one, leaving the earlier fields applied | Parses every field first and restores nothing on an error | Partial restores leave the agent in a state no snapshot described; the success path is the same |
| `take_snapshot` interrupt `context` | `InterruptState.toJSON` returns the live `context` object, so a snapshot changes when the agent later edits its context (ts-bugs.md) | The snapshot is a copy | A snapshot is a point-in-time capture |
| `AgentMetrics.toolUsage` and `accumulatedData` | Getters: `toolUsage` returns each tool's metrics spread with computed `averageTime` and `successRate`; `accumulatedData` returns `{ usage, metrics }` | `AgentMetrics::tool_metrics()` (and `tool_metric(name)`) yield `ToolMetricsData`, whose `average_time()` and `success_rate()` compute the same values; `accumulated_usage()` and `accumulated_metrics()` return the two halves of `accumulatedData` | The computed fields live on the per-tool type, so a second view of the same data would duplicate it |
| A cancel through an external `cancelSignal` | An `AbortSignal` only aborts; the final message is `Cancelled by user` | `InvokeOptions::cancel_signal` is a `CancelSignal` whose `CancelHandle` takes `CancelOptions`: its `message` becomes the final message unless the agent's own cancel set one, and `after_current_tools` defers the external cancel like the agent's | One cancel handle type for both paths; ignoring the options on the external path would accept and drop them |
| The error `AfterModelCallEvent` hooks see when a cancel stops a model call | `CancelledError` (`name` `CancelledError`, `Agent invocation cancelled`) | `Error::Other` with the text `Agent invocation cancelled` (`name()` is `Error`) | TS doesn't export `CancelledError`; Rust keeps it crate-internal |
| Breaking out of the agent stream (dropping `AgentStream`) | `for await` + `break` drains the generator at once: without a prior `cancel()` history keeps the open user turn; with one, the cancel message closes it; `AfterToolsEvent` (mid-batch) and `AfterInvocationEvent` hooks run during the break | A drop is a cancel: the invocation's signal is cancelled, running tool tasks are aborted, and an open user turn is closed with the cancel message (`Cancelled by user` or the stored `message`) unless the turn is paused on an interrupt. `MessageAddedEvent` for that message and `AfterInvocationEvent` run at the start of the next `invoke`, `stream` or `shutdown`; `AfterToolsEvent` doesn't run for the dropped batch. Dropping the agent with those hooks pending logs a warning | `Drop` can't await hooks, and a history ending on a user turn isn't re-invokable on every provider |
| Bedrock throttling on the initial call | `ThrottlingException` from `send` is rethrown as the AWS error and not retried by the default retry strategy | `ModelThrottledError`, retried by default | Section 10 maps 429 to throttled; see the TS bug list |
| Bedrock transport failures | The AWS SDK error is rethrown | `ModelNetworkError` (connection and timeout failures) | Section 10: transport failures map to `ModelNetworkError` |
| Bedrock `additionalArgs` with a key that is not a Converse request member | Dropped silently by the SDK serializer | The call fails with `key=<k> \| additionalArgs key is not a Converse request field` | Accepted-but-ignored config is worse than an error |
| Bedrock `modelMetadataEvent.trace` | The SDK trace object as returned | The same JSON keys without automated-reasoning findings and invocation usage/coverage; object keys of `additionalModelResponseFields` sorted | The Rust SDK types have no serde; detection of blocked policies is unchanged |
| Bedrock JSON documents in requests (tool schemas, tool inputs, `additionalModelRequestFields`) | Key order as written | Key order of a hash map, stable within a process for repeated values | `aws_smithy_types::Document` objects are `HashMap`s |
| Bedrock CountTokens skip list | Process-wide, cleared with `BedrockModel.clearCountTokensCache()` | Per model instance, no clear function | No process-global mutable state |
| Bedrock user agent | `<customUserAgent> strands-agents-ts-sdk` | App name `strands-agents-rs-sdk`, or the `SdkConfig` app name when one is set | `AppName` can't hold a space; each SDK identifies itself, with the name the MCP handshake uses (P-158, P-803) |
| Bedrock request timeout | Socket inactivity timeout of the Node handler; handler instances keep their own | SDK read timeout; other `SdkConfig` timeouts kept | Closest SDK setting |
| Anthropic connection and timeout failures | The SDK's `APIConnectionError`/`APIConnectionTimeoutError` reach the agent wrapped in `ModelError`, so `DefaultModelRetryStrategy` doesn't retry them | `ModelNetworkError` (after the transport's own two retries), which `DefaultModelRetryStrategy` retries | Transport failures are `ModelNetworkError` across providers |
| Pre-built Anthropic clients | `AnthropicModelOptions.client` takes any Messages API client, such as `AnthropicBedrock` | No `client` option; `AnthropicModel` always talks to the Anthropic Messages API (base URL configurable) | The option takes a vendor SDK object; Bedrock-hosted Claude goes through `BedrockModel` |
| Anthropic `anthropic-version` default | Follows the installed `@anthropic-ai/sdk` major: `2023-06-01` on 0.x, `2026-10-21` from 1.0 | Always `2026-10-21` unless a header pins one | Rust reproduces the 1.x SDK transport |
| Anthropic error texts that name options | `'apiKey' option`, `the default for @anthropic-ai/sdk <version>`, `clientConfig.defaultHeaders['anthropic-version']` | `'api_key' option`, `the AnthropicModel default`, `client_config.default_headers['anthropic-version']`; the rest of each text is the same | The messages name the Rust options |
| Anthropic client environment | The SDK also reads `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_LOG`, `ANTHROPIC_WEBHOOK_SIGNING_KEY` and its credential profiles | Only `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL` and `ANTHROPIC_CUSTOM_HEADERS` | Strands requires an API key; the others configure SDK features Rust doesn't have |
| Anthropic request headers | The SDK sends `User-Agent: Anthropic/JS <version>` and `x-stainless-*` platform and retry headers | Neither | They describe the JS SDK and its runtime |
| `default_headers` forms | `defaultHeaders` accepts records, tuples and `Headers`, with `null`/`undefined` values left out | One `http::HeaderMap`; names are case-insensitive and multi-valued | Rust-native header type |
| A plugin's `initAgent` fails | Every later `initialize()` rejects with the same error object | The first call returns the plugin's error; later calls return an `Error::Other` with the same message | `Error` isn't `Clone`, so the registry keeps the message |
| The model plugin's stateful check | `ModelPlugin` captures the model given to the constructor | Captures the agent's model at the first `initialize` | Plugins are assembled at `initialize`, so `set_model` before the first call is honoured |
| OpenAI connection and timeout failures | The SDK's `APIConnectionError`/`APIConnectionTimeoutError` reach the agent untouched, so `DefaultModelRetryStrategy` doesn't retry them | `ModelNetworkError` (after the transport's own two retries), which `DefaultModelRetryStrategy` retries | Transport failures are `ModelNetworkError` across providers |
| Pre-built OpenAI clients | `OpenAIModelOptions.client` takes any `OpenAI` client instance | No `client` option; the model always builds its own client (base URL, key, headers, retries and timeout configurable through `OpenAIClientConfig`) | The option takes a vendor SDK object |
| OpenAI client options | `clientConfig` takes every vendor `ClientOptions` field (`fetch`, `logger`, `defaultQuery`, `workloadIdentity`, `provider`, ...) | `OpenAIClientConfig` has `base_url`, `api_key`, `organization`, `project`, `default_headers`, `max_retries`, `timeout` | The others configure the JS SDK itself |
| Chat Completions tool-call events | Each tool-call delta is emitted as it arrives, so parallel calls' argument deltas interleave and a tool block can open inside the text block | Deltas are gathered by `index`; at the finish chunk the text block closes, then each call is emitted whole (start, its argument deltas, stop) in index order | TS emits blocks the aggregator can't attribute (see ts-bugs) |
| Bedrock Mantle credentials | `credentials` takes an `AwsCredentialIdentity` or a provider function | `credentials` takes an `aws_credential_types::provider::SharedCredentialsProvider` (static `Credentials` convert into it) | The Rust AWS SDK's credential type |
| Middleware context `agent` | The live agent | A `ToolAgent` view taken when the chain starts (`context.agent()`) | The chain runs while the loop holds the agent mutably; handlers read history and state through the view |
| Hooks on events a model or tool chain yields | Callbacks run on every event the chain yields, including injected ones | `ModelStreamUpdate`, `ContentBlock` and `ToolStreamUpdate` records get their hooks; other injected records pass through without hooks | Hooks take live events, and other live events can't be rebuilt from a record |
| `AgentStreamContext.options` and `args` | Shared by reference; the terminal reads `ctx.options` | Owned copies; the pass reads only `options.structured_output_schema`, and replaced `args` (compared by value) replace the hook-processed input | Invocation-wide options (state, cancel signal, limits) are bound before the chain starts |
| `AgentStreamStage` `next` run twice at once | Two interleaved runs of the loop | The second run fails with `the agent stream is already running; a middleware ran \`next\` twice at once` | The pass borrows the agent mutably; sequential reruns work |
| A stage stream that ends without a result | A generator always returns (possibly `undefined`) | `the <stage> middleware chain ended without a result`: it fails the invocation for `agentStream`, `invokeModel` and, under the sequential executor, `executeTool`; under the concurrent executor it is that tool's error result and the turn goes on (`agent::run::tests::middleware::chain_without_result`) | Streams have no return value |
| An `ExecuteToolStage` handler that panics | A throwing handler fails the invocation | A panic becomes an error tool result, like a panicking tool; a returned error fails the invocation as in TS | Matches the tool panic contract (section 10) |
| Background task cancel detection | A tool error named `AbortError` makes the task `cancelled` | A failed result after the task's own cancel signal fired makes it `cancelled`; any other failed result is `failed` | Rust errors carry no name |
| Background tool view | Tools see the live agent | Tools see the `ToolAgent` view of the batch that submitted them, with the task's cancel signal and interrupt state | The live agent is borrowed by the running loop |
| Background tool metrics | Recorded on the agent's meter | Recorded on the run's own telemetry, not in `AgentResult` metrics | Local traces and metrics share one handle in Rust |
| Background task ids | `crypto.randomUUID()` (v4) | UUID v7 | Same as message tracking ids |
| `BackgroundTasksConfig` tool selectors | A `Tool` or a registered name | A registered name (`"*"` for all) | TS reads `tool.name` anyway |
| MCP client name sent in the handshake | `strands-agents-ts-sdk`, version `0.0.1` | `strands-agents-rs-sdk`, the crate version | Each SDK identifies itself (P-230) |
| MCP `url` given as a `URL` object | Accepted | `url` is a string | Rust has no `URL` union here |
| MCP `requestTimeout` / `ttl` | Only in `tasksConfig` (MCP tasks) | Not available; tasks are out of scope; the SDK 60 s default applies to every request | P-237 |
| Invalid MCP header names or values in `headers` | Fail when the request is sent | `McpClient::new` fails with `header=<name> \| invalid header name: ...` | Rust builds typed headers up front |
| MCP progress token | Sent only when a progress callback is set | `rmcp` sends a `progressToken` on every request | `rmcp` assigns tokens itself (P-244) |
| MCP progress callback failures | A throw or an async rejection is caught and logged | A panic is caught and logged; callbacks are synchronous | Rust callbacks are `Fn`, not async |
| MCP tools-list change in an agent | Registry updated as the notification is handled | Applied before the agent's next model call | The agent owns its registry (P-245) |
| MCP trace context without telemetry | Injected from the active OpenTelemetry span | Injected only with the `otel` feature, from the current `tracing` span's OpenTelemetry context, with the W3C propagator | Telemetry is opt-in in Rust (P-247) |
| `loadServers` regex filters | JavaScript `RegExp` syntax; an invalid pattern reports the JS `SyntaxError` text | `regex` crate syntax (no look-around or backreferences); the message keeps the TS prefix `Server "<name>": invalid regex in toolFilters.<key>: "<pattern>": SyntaxError: ` followed by the `regex` error | No JS regex engine in Rust |
| `loadServers` entry with `tasksConfig` | Validated and used for MCP tasks | Fails that entry with `MCP tasks ("tasksConfig") are not supported in Rust yet` | MCP tasks are out of scope for v0.1 |
| `loadServers` file errors | Node `ENOENT` / `JSON.parse` messages | `std::io` / `serde_json` messages | Platform error text |
| MCP client-credentials `resource` parameter | The protected-resource-metadata `resource` when that metadata exists, otherwise omitted | Always the server url | `rmcp` requires a `resource` and does not expose the discovered one (P-246) |
| Responses stream that ends without `response.completed` or `response.incomplete` | Finished with stop reason `endTurn` | Fails with `ModelError` "Stream ended without completing a message" | The TS behaviour returns a truncated response as complete (see the TS bug list) |
| Anthropic SSE frame `event: error` with no `data:` line | The vendor SDK throws an API error "(no status code or body)" | The frame is dropped (`eventsource-stream` skips events with empty data); the stream then fails with "Stream ended without completing a message" or carries on | `eventsource-stream` is the decoder; the Messages API sends a JSON body with every `error` event |
| `sandbox: false` | On Node, the same as an unset key: the agent runs on the host | `SandboxSource::Off`: `agent.sandbox()` and every tool that needs a sandbox fail with `DefaultNotConfiguredError` ("No Sandbox configured. ...") | The design makes the opt-out explicit (P-264); Rust has no environment without a host default |
| Default sandbox instance | One process-global `NotASandboxLocalEnvironment` registered at import | Each agent without a `sandbox` key builds its own (the type is stateless) | No process-global registration (P-263) |
| Process termination | `SIGTERM`, then `SIGKILL` after 1 s, to the direct child only | The same signals sent to the child's whole process group (job object on Windows); dropping the stream kills the group | Child processes never outlive their tool (P-266) |
| `listFiles` order (local) | `localeCompare` | Lowercase name, then bytes | No ICU collation (P-268) |
| Execution env map | `Record<string, string>` in insertion order | `BTreeMap`, so `export` assignments are in key order | Deterministic; the shell result is the same (P-260) |
| `bash` session scope | One module-global map of sessions; killed by `process` exit/SIGINT/SIGTERM handlers | Sessions belong to the tool instance and die with it (or with the agent) | No process-global state or signal handlers (P-270) |
| `bash` stderr | The result is taken when the stdout sentinel arrives; stderr written after that is lost | A second sentinel on stderr; the result waits for both | The command's stderr is always in `error` (P-270) |
| Vended tool validation texts | zod messages | `jsonschema` messages, except the zod custom messages TS tests assert, which are kept | P-51, P-269 |
| `http_request` response body | Read in full | Read as a stream and capped at 10 MiB (`Response body exceeds the 10485760-byte limit: ...`) | Section 11 item 32 (P-272) |
| `http_request` `statusText` | The server's reason phrase | The canonical reason phrase for the status | `reqwest` doesn't expose the received phrase (P-272) |
| `notebook` fractional `insertLine` | Spliced at the truncated index | `Line number out of range` | P-271 |
| `web_fetch` markdown | `turndown` output | `htmd` output with the same options and rules (title heading, dropped elements, safe images and links); whitespace and escaping can differ | No turndown port in Rust; `htmd` follows turndown's rules (P-280) |
| `web_fetch` `maxContentChars` | Counts UTF-16 code units | Counts `char`s | Section 7.3 (P-280) |
| `web_fetch` `statusText` | The server's reason phrase | The canonical reason phrase for the status | `reqwest` doesn't expose the received phrase (P-272, P-280) |
| `subagent` `maxDepth` | Any positive integer `number` | `u32`, zero rejected | Negative and fractional values are unrepresentable (P-281) |
| Conversation manager hooks | A subclass that overrides `initAgent` without calling `super` loses the overflow and proactive hooks | The agent always installs both base hooks; `ConversationManager::init_agent` only adds hooks | A trait default can't be "called as super"; the adapter plugin installs them (P-96) |
| Failed overflow reduction | `reduce` throwing during overflow recovery propagates its error out of the loop (`SummarizingConversationManager` sets the overflow as `cause`) | The failure is logged and `retry` stays unset, so the call ends with the original `ContextWindowOverflowError`; `reduce` itself returns the summarization error | Hooks can't fail (P-49, P-96) |
| `compressionThreshold` | `NaN` passes validation | `NaN` is rejected with the range error | `!(t > 0 && t <= 1)` (P-96) |
| Tool result truncation | Slices UTF-16 code units, so a cut can split a surrogate pair | Counts and cuts UTF-16 code units like TS; a split pair becomes U+FFFD | Rust strings hold no lone surrogates (P-96) |
| Token-usage status percentage | `toFixed(1)` of the double ratio | Rounds the exact ratio of the integer counts half up; can differ from TS only where the double ratio sits on the other side of a tie | Integer arithmetic (P-96) |
| `mcp_router` connections of an agent that is gone | Closed in the background when the agent is garbage collected (`FinalizationRegistry`, best effort) | Closed at the start of the router's next call, or when the router is dropped | Rust has no finalizer on the agent's identity (P-252) |
| Session restore at initialization | `SessionManager` restores the latest snapshot in an `InitializedEvent` hook; a failed read or load throws out of `initialize`/`invoke` | The restore runs in the session manager's `init_agent`, at its slot in the plugin registration order; a failure fails `initialize`/`invoke` the same way. `InitializedEvent` hooks (user hooks included) see the restored history | Hook callbacks can't fail in Rust, and a swallowed restore error would let the next save overwrite the stored session |
| A session save that fails inside a hook | The error from the `MessageAddedEvent`, `AfterModelCallEvent` or `AfterInvocationEvent` save propagates out of the invocation | Logged at error level (`session_id=<..>, error=<..> \| failed to save the session snapshot`); the invocation result is unchanged. `save_snapshot` called directly returns the error | Hook callbacks can't fail in Rust |
| Generic namespace view with a trailing-slash prefix | `namespace(storage, 'prefix/')` lists keys with characters cut off (`'ey'` for `key`) | Lists whole keys (`key`) | TS bug (see the TS bug list) |
| `LocalFileStorage` scratch-file name | `<path>.__strands_tmp_<uuid v4>` | `<path>.__strands_tmp_<uuid v7>` | The crate enables only the `uuid` v7 feature; the name is never persisted and listings skip both |
| Bedrock region | AWS SDK chain, `us-west-2` when "Region is missing"; the instance metadata lookup keeps a negative cache | Option, `SdkConfig`, `AWS_REGION`, shared profile, EC2 instance metadata, then `us-west-2` (no negative cache for the metadata lookup) | Explicit chain with a test seam; the order is the JS SDK's (`AWS_DEFAULT_REGION` is not read) |
| Dropping a pending `bash` call | No equivalent: a pending run can't be dropped | The session is killed with the dropped call; the next call starts a fresh session (variables and directory reset), as after a timeout | A dropped future can't finish reading its command's output, and keeping the session would hand that output to the next call (P-283) |
| A dropped first `initialize` | Can't happen: a consumer break doesn't cancel an in-flight `initAgent` | The next call resumes at the plugin whose `init_agent` was awaiting and runs it again from the start | A dropped future stops at any `await` (P-98) |
| Cancelling an MCP tool call while an input-required elicitation callback is pending | The callback's `signal` aborts; the call rejects once the callback settles | The callback's `cancel_signal` is cancelled and the call returns the abort error at once; the callback's future is dropped | Dropping a future is how Rust cancels it, and an agent cancel must not wait on a user-facing prompt (P-256) |
| MCP output-schema mismatch text | `Structured content does not match the tool's output schema: data/forecast must be string` (ajv wording) | `Structured content does not match the tool's output schema: data/forecast 42 is not of type "string"` (`jsonschema` wording after the same `data<path>` prefix) | The crate validates with `jsonschema`, not ajv; the prefix, error codes and the other two texts match (P-256) |
