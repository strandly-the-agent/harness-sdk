# Divergences from TypeScript

Every user-visible behaviour difference from the TypeScript harness, with the reason. A divergence never changes a cross-SDK wire or persisted format.

| Area | TS behaviour | Rust behaviour | Reason |
|---|---|---|---|
| Model strings | `google/`, `ollama/` and `litellm/` build Gemini and OpenAI-compatible models | `model provider "google" is not supported in Rust yet` (also `ollama`, `litellm`) | Rust v0.1 has Bedrock, Bedrock Mantle, Anthropic and OpenAI (#60) |
| Unknown model provider | `Supported providers: anthropic, bedrock, bedrock-mantle, google, litellm, ollama, openai` | `Supported providers: anthropic, bedrock, bedrock-mantle, openai` | the list names what Rust builds (P-831) |
| Disabled provider | every provider is importable | `model '<spec>' requires the strands feature "<feature>"` when the provider's cargo feature is off | providers are cargo features in Rust |
| `supports_thinking`, `supports_web_search` on `google/...` | `true` | `false` | Google is not a Rust v0.1 provider |
| `web_fetch` summarizer for `ollama/`, `litellm/` | warns and reuses the main model | the unsupported-provider error | the main model itself can't be built |
| `supportsMedia` on a model instance | `false` only for a `BedrockModel` instance with an `openai.` family id | `false` for any instance whose model id has an `openai.` family | `Model` has no downcast (P-832) |
| `effort` outside the enum | `resolveModel` throws `Effort "x" is not valid. ...` | `Effort` is an enum; the same text comes from parsing a name (`parse_effort`) | typed API (P-833) |
| `edit` replacement text | `content.replace(old_str, new_str)` expands `$&`, `$$` and the other replacement patterns in `new_str` | `new_str` is written literally | The TS behaviour is a bug; the tool documents `new_str` as the replacement text |
| `read`, `write`, `edit` without a tool context | `Tool context is required for read.` (and `write`, `edit`, `web_fetch`) | Not reachable | A Rust tool always gets a `ToolContext` |
| `web_fetch` transport | `makeWebFetch` throws `web_fetch transport must be 'curl' or 'direct', got "…".` | Not reachable | `WebFetchTransport` is an enum |
| `interventions`: invalid value | `resolveInterventions` throws `Invalid interventions value …; expected a preset name, a policy string, or a handler instance.` | Not reachable | The typed option holds only a string or a handler (P-919) |
| `interventions`: Cedar dependency missing | `Cedar policy '<path>' needs the optional '@cedar-policy/cedar-wasm' dependency; install it to use Cedar interventions.` | Not reachable | Cedar is compiled into the Rust SDK, not optional (P-919) |
| Telemetry without the `otel` feature | `OTEL_TRACES_EXPORTER` always wires the exporters it names | Logs once `OTEL_TRACES_EXPORTER is set, but strands-harness was built without the `otel` feature; tracing stays off.` and exports nothing | The OpenTelemetry exporters are behind the `otel` cargo feature |
| `web_fetch` text cap | The first 50,000 UTF-16 code units, which can end in half of a surrogate pair | The same cut, minus a character it would split | A Rust string cannot hold a lone surrogate |
| `web_fetch` direct transport failures | `Failed to fetch <url>: fetch failed` (Node's `fetch` message), and `HTTP <status> <statusText>` with the server's reason phrase | The `reqwest` error text, and the status's canonical reason phrase | The failure text comes from the HTTP client, and `reqwest` gives the status code, not the server's reason phrase |
| `web_search` Exa tool availability | Always exported | `make_exa_web_search` and `exa_web_search` need the `mcp` cargo feature (on by default) | The tool is built over the SDK's MCP client, which is behind the SDK's `mcp` feature |
| `web_search` Exa call timeout | `AbortSignal.timeout(30_000)` passed to `callTool` | `McpCallToolOptions.timeout` of 30 s | The SDK's MCP client takes the timeout directly; the failure text is the client's timeout error |
| `web_search` backend errors | A backend may throw any value; the tool reports `err.message`, else `err.name` | A backend returns `WebSearchError`; an empty message is reported as `Error` | Rust backends return a typed error |
| `programmatic_tool_caller`: inner call pipeline | An inner call runs `beforeToolCall` hooks, the tool and `afterToolCall` hooks; no tool middleware, `AfterToolCallEvent.retry`, tool span or stream updates | An inner call goes through `ToolAgent::call_tool`: hooks and interventions, the `ExecuteToolStage` middleware, the tool span, and an `AfterToolCallEvent` retry; stream updates are dropped | PROMPT.md decision #62: the SDK exposes one public way to run a tool as the executor does, in place of TS's access to the private hook registry |
| `programmatic_tool_caller`: hook cancel text | A hook cancel without a message raises `Tool '<name>' was cancelled by a hook.` | The executor's text, `Tool cancelled by hook` | The cancel is applied by the SDK pipeline |
| `programmatic_tool_caller`: a tool that interrupts | The inner tool's `interrupt()` throws `Interrupts are not supported from programmatic_tool_caller.` | Reported like a hook's approval request: `Tool '<name>' needs approval (<reason>), which programmatic_tool_caller cannot prompt for; call it as a normal tool call instead.` | `call_tool` returns every interrupt the same way |
| `programmatic_tool_caller`: Monty runtime | `@pydantic/monty` 0.0.23 in a worker process, or WebAssembly in-process with guest compute capped at 5 s | The `monty` 1.5 crate in-process on the blocking thread pool; no separate cap | The Rust crate is the interpreter itself; there is no worker to isolate a crash |
| `programmatic_tool_caller`: `eval` | `eval` is not defined in the sandbox (`NameError`) | Monty 1.5 implements `eval` and `exec` inside the sandbox | Newer Monty; the code still reaches nothing outside the sandbox |
| `programmatic_tool_caller`: cancel or timeout during guest compute | The worker is torn down at once | The run is reported cancelled at once, and the abandoned step runs on its thread until the VM duration limit; a wall-clock timeout that passes during guest compute is reported when the step ends (the VM duration limit is lowered to the timeout) | An interpreter step cannot be interrupted from outside in-process |
| `programmatic_tool_caller`: a tool call that is never awaited | The call starts when the function is called | The call starts when the code awaits it (or gathers it); a call that is never awaited never runs | Host calls are polled while the code waits, so no tool call outlives the run |
| `programmatic_tool_caller`: structured MCP results | An MCP `structuredContent` is handed to the code as data | The code receives what the SDK put in the tool result: a lone `json` block or JSON text as data | `ToolResultBlock` has no `structuredContent` field |
| `programmatic_tool_caller`: output cap | 200 000 UTF-16 code units | 200 000 Unicode scalar values | Rust strings; the same for ASCII |
| `programmatic_tool_caller`: which tools are callers | By object identity | By tool name (every name a caller was made with in the process) | The `Tool` trait has no identity; see P-873 |
| `programmatic_tool_caller`: suspension limit text | Monty binding's text | `RuntimeError: suspension limit exceeded: more than 1000 host round trips` | The Rust host enforces the budget itself |
| `programmatic_tool_caller`: unreachable hooks | Refuses the call with `Cannot reach the agent's hooks to gate the call to '<name>'; refusing to run it ungated.`; `No agent available..` without an agent | Neither state exists | `ToolContext` always has an agent and `call_tool` always reaches the hooks |
| `subagent` `last_messages` | `Number(raw.last_messages)` accepts a one-element array (`[5]` is 5) | An array or object is not a number, so no cap is applied | The schema declares an integer; only JSON numbers, numeric strings and booleans are coerced (P-897) |
| `subagent` `context` choice | An option with no value whose name is not a context mode reaches the builder as that string and shares nothing | The same option resolves to `ContextMode::None` | `ContextMode` is an enum; the child sees the same prompt (P-892) |
| `EnvironmentContext`: `AGENTS.md` cut at the 16,000 cap | `text.slice(0, 16000)` cuts at a UTF-16 code unit, so a cut inside a surrogate pair leaves a lone surrogate | The cap is counted in UTF-16 code units too, but a character the cut would split is dropped whole | A Rust `String` cannot hold a lone surrogate; text outside the BMP at the cut is the only case that differs, by one code unit |
| Portable config: module references | `harnessAgentOptionsFromConfig` loads each referenced module (TypeScript; Python is `Cannot load Python module`) | Returns `module references are not supported in Rust yet`, with ` (language "<language>")` when the reference names one; normalization keeps the references | Rust cannot load a TS or Python module (#31) |
| Portable config: `agentConfig` | Every key is spread into the options untyped, before the top-level keys; a value of the wrong shape fails later or not at all, and a key `Agent` does not read is ignored silently | The same keys are applied with the same precedence, each one typed: the SDK keys `name`, `description`, `id`, `systemPrompt`, `messages`, `appState`, `modelState`, `printer`, `auxModel`, `baggageAttributes`, `traceAttributes`, `toolExecutor`, `sandbox: false`, `retryStrategy: null` or `[]`, `backgroundTasks`, and the harness keys `instructions`, `caching`, `builtinTools`, `builtinPlugins`, `mcpServers`, `interventions`. A wrong type is an error when the options are built (`agentConfig.<key> is invalid: ...`, or `Invalid agent config:` with the path under `agentConfig.` for `builtinTools`, `builtinPlugins`, `interventions`). `tools`, `plugins`, `conversationManager`, `structuredOutputSchema`, `sessionManager`, `memoryManager`, `checkpointing`, `storage`, a `sandbox` other than `false` and a `retryStrategy` other than `null` or `[]` are the error `agentConfig keys are not supported in Rust: <keys>.` or `agentConfig.<key> is invalid: ...`. A key neither SDK reads is dropped with the warning `Ignoring unknown agentConfig keys: <keys>.` | `AgentConfig` is typed; the rejected keys hold live objects in TS (or, for `checkpointing`, have no Rust field), and a key that cannot take effect is an error rather than a silent drop (PROMPT.md section 11 item 37) |
| Portable config: non-JSON values | `agentConfig` and `mcpServers` values that are not JSON are reported as `must contain only JSON-compatible values.` | Cannot occur | The input is a `serde_json` value |
| `HarnessAgentOptions` passthrough | SDK `AgentConfig` keys sit beside the harness keys; the six harness-owned keys are absent from the type | SDK keys are in `agent_config`; setting one of the six there is `HarnessError::PassthroughOption` | Rust has no `Omit`; a typed error replaces the type error |
| `mcp_servers` option | `Record<string, McpServerConfig>` | `McpServersOption::Servers` holds the JSON map (`From` a typed map with the `mcp` feature) | `McpServerConfig` exists only with the `mcp` feature |
| `harness_agent_options_from_config` | Async; `~` from `os.homedir()` | Synchronous; `~` from `HOME`, then `USERPROFILE` | Nothing to await without module loading; no home-directory dependency |
| Portable config: `subagent.maxDepth` | Any non-negative safe integer, kept as given | A value above `u32::MAX` is held (and serialized back) as `u32::MAX` | The depth is a `u32`; no delegation chain reaches either bound |
| Shell probe cache | One module-wide `WeakMap`: a sandbox is probed (`echo "${PSEdition}"`) once per process | Each tool or plugin that asks owns a `ShellCache`: a sandbox is probed once per consumer | No process-global state; the answer is the same (P-980) |
| `builtin-tools.ts` `mcpClientsByClientName` | The unnamed-client warning says `application_name` where TS says `applicationName` (P-953). |
| `builtin-tools.ts` `webSearchMode` | `web_search: 'exa'` without the `mcp` feature is `HarnessError::FeatureDisabled` (P-951). |
| `agent.ts` `createHarness` | Built-in plugins and an existing `AgentSkills` are recognised by plugin name, not type (P-958). |
| `agent.ts` `createHarness` | `caching: 'auto'` passed explicitly behaves as not passed (warns, never errors) (P-957). |
| `agent.ts` `createHarness` | `mcp_servers` without the `mcp` feature is an error (P-961). |
| `web_fetch` URL cache | One tool instance keeps one page per URL for 15 minutes, without a bound, and serves it to every agent that shares the tool | At most 64 live entries; an entry fetched through a sandbox (the `curl` transport) is served only to agents on that sandbox | A long-lived tool must not grow without bound, and a page fetched under one sandbox's network controls must not reach an agent on another |
| JS `trim` | `String.prototype.trim` | The same character set at every site that mirrors a TS `.trim()` (U+FEFF trimmed, U+0085 kept) | Byte-observable text matches TS |
| `Agent` intervention handlers | No public accessor; the registry is the private `_interventionRegistry` | `Agent::interventions()` lists the handlers in registration order | Callers and the harness tests can check which handlers an agent runs without reaching into private state (P-1050) |
| `@strands-agents/harness/internal` entry point | a second package entry re-exports the factory plumbing (`normalizeHarnessAgentConfig`, `resolveModel`, `resolveMemory`, `resolveInterventions`, `resolveBuiltinTools`, `enabledBuiltinTools`, `builtinToolConfig`) for the TypeScript CLI | no such module; the same functions are crate-private | TS marks the entry `@internal`, and the CLI that consumes it stays TypeScript (P-1070) |
| Flushing spans at exit | The SDK's `setupTracer` flushes the tracer provider on Node's `beforeExit`; the harness exports nothing for it | The caller calls `shutdown_telemetry().await` once before the process exits; without it the spans still in the OTLP batch are lost. After it, agents export no spans | Rust has no process-exit hook (P-1130) |
| Several agents on one `McpClient` (`tools/list_changed`) | `Agent.initialize` assigns the client's single `onToolsChanged`, so only the last agent to initialize follows a tools-list change, and a consumer callback set earlier is replaced | Every live agent that listed the client's tools applies the change before its next model call; a dropped agent is removed from the client; a callback set with `set_on_tools_changed` is left in place and called too | TS bug (see the TS bug list): a delegate on the parent's client stopped the parent's refresh (P-1140) |
| Background task that asks for input after the model ended its turn, once the caller answers (`waitForCompletion` on) | The model is called with a history ending in its own assistant message; its reply is a second assistant message in a row, and the task result follows on a later call | No model call until the resumed task settles (or asks again); its result is delivered first, so the request ends in the delivered tool result. With `wait_for_completion: false` the sequence is the TS one | TS bug (see the TS bug list); the request sequence is the one an uninterrupted run produces (P-1141) |
| `createHarness`: recognising a consumer plugin that stands in for a built-in one | By class (`instanceof Todos`, `instanceof EnvironmentContext`, `instanceof AgentSkills`): the built-in is not added | `AgentSkills` by its fixed plugin name. `Todos`: the built-in is not added when a consumer plugin has its name or vends the same tools (the `todo_write` spec), so a `Todos` under a custom name is recognised; another plugin with a different `todo_write` still fails with the TS collision error, and one that vends an identical `todo_write` spec is taken for a `Todos`. `EnvironmentContext`: not added when a consumer plugin has its name; otherwise the built-in is added (it is in the agent's plugin list) but injects nothing into a user turn in which an earlier plugin already wrote an `<environment>` block, so the model sees one block, the consumer's. A plugin that is not an `EnvironmentContext` and injects a block starting with `<system-reminder>`, `<environment>` also silences the built-in for that turn | `dyn Plugin` has no downcast and the public API takes no `Any` or `TypeId` (decision #15); the observable results of the TS rule are kept (P-958, P-1142) |
